### 要拍板的事

**1. 选哪张基准图。**

- A：项目经理对话三栏。一张图里有左栏、气泡、卡片、右栏任务图、输入框和水果底色，覆盖的样式最多。
- B：总助工作台。中性色，没有水果底色，内容少。
- C：资料页。只代表设置这一类一行一项的界面。

推荐 A。设置类界面的样子由 `docs/ui-standard.md` 第 9 条和从基准图提炼的风格说明补上，不需要第二张基准图。

**2. 和风方向要不要并进来。**

- 不并：基准用现在的 main，PR #305 继续挂着。
- 先并：先定 PR #305 合不合，合了再重截基准图，循环晚几天开始。

推荐不并。PR #305 改的是底色、字色、刀的头像和图标，不动布局、间距和字号。循环修的主要是后面这几样，换了配色照样有效。以后决定合 PR #305，换一张基准图、改风格说明里的配色一节，再全量评一次就行，这套工具本来就是为“大改之后再跑一遍”做的。

### 项目经理已定，要改就说

**评委用哪两家。** Antigravity 的 `gemini-4-carbon` 加 Claude Code 的 `opus`。改界面的是 Claude Code 的 `fable`。两家不同公司的模型看问题的角度不一样。分数取两家里低的那个，所以 Claude 这一家只能把分往下拉，不会因为偏爱同门改的界面把分抬上去。

**9 分怎么算。** 分数不由评委凭感觉给。评委只列发现，每条发现标严重度，分数按固定的表从发现算出来。四项（风格一致、行业标准、美学、使用体验）每项都不低于 9，两家评委都不低于 9，这张图才算到 9 分。一项 9 分的意思是这一项没有 P0、P1、P2 的发现，P3（吹毛求疵）不超过两条。严重度的定义和整张表见 3.3 节。不用平均分，是因为平均会让“面板被裁掉但其他三项好看”的界面过关，今天你自己截图报的那个问题就是这种。

**评委 Worker 的数量。** 这台 Mac 吃紧，同时在跑的评委 Worker 不超过 6 个，一次评审总共不超过 10 个。做法是每个评委一次评 28 张图。28 张一批靠不靠得住，校准时和 14 张一批一起测，用过了门槛的最大一档。28 张过不了就用 14 张一批，分波次串行跑，不加并发，这时一次评审是 20 个 Worker。

**轮数。** 最多修 6 轮；连续 2 轮没进展就停下来，把剩下的问题列给你。

## 1. 用户目标

用户原话：

> 帮我设计一个界面优化循环，大致流程是这样，先确定一张基准图代表我们产品的整体风格，然后去截各个界面比如左栏，中间对话，右边的worker，所有的设置页面，包括额度这种细节都要考虑到。然后让模型根据我们这个产品的整体风格，和行业严格标准，和艺术家，美学家的美学表现，和用户使用体验对各个页面进行打分，直到所有页面都能达到9分

我的理解：要一套能反复跑的流程和工具。一条命令截下全部界面，评委按写明的标准打分，不到 9 分的改，改完全量重评，直到每个界面都到 9 分或到了轮数上限。以后界面大改时能再跑一遍。

## 2. 现状

- 推断：全仓要评的界面是 112 个，按窗口宽度展开是 133 张图。清单是我对照 `docs/ui-standard.md:7` 到 `docs/ui-standard.md:547` 的 21 条和 `src/web/components/`、`src/web/mobile/settings/` 的文件逐个列的，数是 `test/ui-polish/screens.ts` 里数出来的。没有逐个打开验证，实现时到不了的界面会让截图命令失败，那时再修清单。
- 实测：main 上没有任何浏览器自动化依赖，`package.json` 的依赖里没有 Playwright、Puppeteer。以前截图是每次在 `/tmp` 里临时装 `playwright-core` 写一个脚本，例如 `/tmp/router-picker-fix/tool/shot.cjs`，或者手写 Chrome 调试协议，例如 `/tmp/w600-demo/shoot.mjs`。脚本里靠 `waitForTimeout` 等固定毫秒，不进仓库，下次重写。
- 实测：账本接受外面给的时钟（`src/daemon/ledger/ledger.ts:79` 的 `now`）。我写了一个试跑脚本（`/tmp/ui-polish-loop/tool/seed.ts`），用 `createLedger` 加固定时钟建了 6 个项目经理、一张带拍板卡的任务图和一条总助简报，再在这个数据目录上起真守护进程（`/tmp/ui-polish-loop/tool/serve.ts`），界面正常显示这些数据。

- 实测：Worker 的沙箱里数据目录是只读挂载的（`docs/write-scope.md:26`），所以 Worker 写不了 `~/.agent-hub/pm-notes/`，每轮的记录要么进仓库，要么放 `/tmp`。

### 3.2 截图工具

| 做法 | 好处 | 坏处 |
| --- | --- | --- |
| Playwright 库，自己写一个按清单循环的入口 | 微软维护，自带固定时钟、关动效、拦请求、手机模拟、等元素出现；一个依赖；输出什么文件我们自己定 | 循环、并发、失败报告要自己写，约一百行 |
| Playwright Test（它的测试运行器） | 自带并发、重试、报告、起服务 | 仓库里已经有 vitest，多一套测试运行器和配置；它围着断言和基准图设计，我们要的是一批图加一份清单 |
| Puppeteer | 成熟 | 没有固定时钟的接口，手机模拟和等待不如 Playwright 全 |
| 继续手写 Chrome 调试协议 | 零依赖 | 等待靠固定毫秒，不稳；每个状态都要自己拼协议消息 |
| Storybook 加 Chromatic 或 Loki | 组件级截图成熟 | 要给每个界面写 story，截到的不是真实拼起来的应用；额度浮层被裁这类问题只在真实页面里出现 |
| vitest 的浏览器模式 | 不加测试运行器 | 跑的是组件测试，起不了守护进程和整页应用 |

推荐第一种，装 `playwright`。试跑用的就是它的 `playwright-core`，6 张图三次重截逐字节一致。

数据从哪来也比了三种：

| 做法 | 好处 | 坏处 |
| --- | --- | --- |
| 真守护进程，种子用账本接口加固定时钟写 | 接口形状永远是真的；设置、分页、历史这些接口不用另写；时间戳固定 | 在忙、流式、额度这类瞬时状态守护进程撑不住，要另想办法 |
| 假后端（照 `test/fake-devices/main.ts` 手写快照） | 什么状态都能摆 | 每个接口都要再写一遍，接口一改就对不上；`/tmp/fusa-work/fake-backend.ts` 就是这样一份只管 5 个接口的临时货 |
| 真守护进程加假 claude 按剧本跑（`test/e2e/harness.ts:141`） | 最真 | 时间戳是真实时间，每次不一样；跑一遍剧本要等 |

推荐第一种，瞬时状态用“补丁”补上：在浏览器这一头改写某个接口的回包，例如把一个会话改成在忙、给 `/api/quota` 填上窗口。补丁有名字，集中在 `test/ui-polish/patches.ts`，清单里按名字引用，改写后的回包仍然按 `src/shared/api.ts` 的类型检查。项目经理定的“隔离的真守护进程、固定种子”不变，补丁只用在真守护进程摆不出来的状态上。

钉死的东西：视口和 2 倍像素比；时区 `Asia/Shanghai`、语言 `en-US`；浏览器时钟（Playwright 的 `clock.setFixedTime`）；种子的时钟；数据目录的路径（主文件夹路径会显示在界面上，不能带随机后缀）；`reducedMotion: "reduce"` 和截图时的 `animations: "disabled"`；这台浏览器的 `localStorage`；非 GET 请求一律拦掉；点开东西之后把鼠标移走再截，免得悬停底色混进图里。

截图只在这台 Mac 上跑。界面用系统字体，Linux 上字形不同，不拿 CI 截的图评分。

### 3.3 评分标准

四项对应用户原话，每项 1 到 10 分。

| 项 | 和什么比 | 评委引用什么 |
| --- | --- | --- |
| 风格一致 | 基准图和从它提炼的风格说明 | S1 到 S6：配色、字号层级、间距节奏、形状、疏密、语气 |
| 行业标准 | `docs/ui-standard.md`、`frontend-rules`、WCAG 2.2 AA、Apple HIG 的 44pt 触控目标 | 直接引条款，如 `ui-standard §11`、`WCAG 1.4.3`；机器量出来的引 `machine:clipped` |
| 美学 | 有出处的八条原则 | A1 到 A8 |
| 使用体验 | 有出处的八条原则 | U1 到 U8 |

“艺术家、美学家”落在 A1 到 A8，每条写了出处和在图上怎么核对，全文在 `test/ui-polish/rubric.ts` 的 `PRINCIPLES`：

| 编号 | 原则 | 出处 | 怎么核对 |
| --- | --- | --- | --- |
| A1 | 层级 | 《Refactoring UI》；眯眼测试 | 把图缩到四分之一，第一眼落在最重要的东西上，主操作只有一个 |
| A2 | 对齐 | Müller-Brockmann 的网格系统 | 数各块左边缘连成的竖线，同一栏里只有一到两条 |
| A3 | 亲疏 | 格式塔的接近律、相似律 | 组内间距小于组间间距，同类的东西长得一样 |
| A4 | 留白 | 原研哉《白》；Rams 十条第 10 条 | 不顶边、不挤，也没有说不出理由的大块空白 |
| A5 | 字体排印 | Bringhurst《The Elements of Typographic Style》 | 一行 45 到 75 个西文字符或 25 到 40 个汉字，行高够，数字等宽 |
| A6 | 色彩纪律 | Itten 的面积对比；Tufte 的最小有效差异 | 中性色为主，强调色面积很小，靠深浅分层级 |
| A7 | 克制 | Rams 十条第 5、10 条；Tufte 的数据墨水比 | 逐个元素问删掉它用户会不会少知道什么 |
| A8 | 细节完成度 | Rams 十条第 8 条；民艺运动的“用之美” | 没有被裁的字，嵌套圆角内小外大，图标粗细一致 |

使用体验的 U1 到 U8 出自 Nielsen 十条、Krug、Fitts 定律、WCAG、Hoober 的拇指热区研究，同样每条写了核对办法。

评委不直接给分，只列发现。每条发现必须引一条规则、标严重度、框出位置、写哪里不对和怎么改。引不出规则的发现不收。

| 严重度 | 意思 |
| --- | --- |
| P0 | 内容看不到或功能用不了：被裁掉、互相盖住、字看不清、点不到 |
| P1 | 不用对比就看得出：明显错位、层级乱、违反标准里写明的条款 |
| P2 | 要和基准图或同类界面对比才看得出：局部不协调、间距档位不对 |
| P3 | 吹毛求疵：一两个像素的光学对齐、措辞可以更短 |

分数按这张表从发现算出来：

| 一项的分 | 这一项的发现 |
| --- | --- |
| 10 | 没有 |
| 9 | 只有一两条 P3 |
| 8 | 1 条 P2，或 3 条以上 P3 |
| 7 | 2 到 3 条 P2 |
| 6 | 1 条 P1，或 4 条以上 P2 |
| 5 | 2 条 P1 |
| 4 | 3 条以上 P1；或这张图上有 1 条 P0 |
| 2 | 这张图上有 2 条以上 P0 |

P0 不分项。内容看不到的界面谈不上风格、美学和体验，任何一条 P0 把四项一起压下去。

这样做的原因：让评委直接报一个 1 到 10 的数，同一张图两次能差两三分，而且说不清 8 和 9 差在哪。让评委列发现，分数的波动只来自“有没有看见这个问题”和“判成几级”，每一分都能指回具体的发现。评委另报一组整体印象分，只用来对账：和算出来的分差 2 分以上，说明评委看见了标准没写到的东西，归因时要看。

输出格式是一张图一个 JSON（`rubric.ts` 的 `scoreCardSchema`）：

```json
{
  "shot": "router.model-picker@desktop",
  "judge": "agy/gemini-4-carbon",
  "run": 1,
  "imageSha256": "…",
  "findings": [
    {
      "rule": "ui-standard §11",
      "severity": "P0",
      "box": { "x": 0.955, "y": 0.1, "w": 0.035, "h": 0.5 },
      "what": "每一行最右边的单选圆点被面板右边切掉一半",
      "fix": "装行的 grid 写 grid-cols-1"
    }
  ],
  "holistic": { "style": 7, "standard": 3, "aesthetic": 5, "ux": 4 },
  "summary": "面板右边被裁"
}
```

这是我在项目经理的设计上加的一样东西，机器检查。截图的同时在页面里量八种硬毛病：内容被裁、横向滚动、可点范围互相盖住、对比度不够（用 Deque 的 `@axe-core/playwright`）、手机上点击区域小于 44px、截断了却没有 `title`、字号不在四档里、外壳文字里有“·”。量出来的直接算成行业标准这一项的发现，也作为事实告诉评委。加它的原因是今天那个面板被裁的问题，修的人是量坐标才确认的（行右边 1283.70px，面板右边 1266.75px）。差 17px 的裁切，模型看缩小后的图不一定看得出。

### 3.4 一页的分数怎么合

1. 每家评委的发现各自按 3.3 的表算出四项。
2. 两家的发现合并。同一张图上框的交并比不低于 0.3，或引了同一条规则，算同一处。
3. P0 到 P2 任何一家提了就计分。P3 要两家都提才计分，一家的吹毛求疵不算。机器量出来的都计分。
4. 每项取两家里低的。页面分取四项里最低的。
5. 归因的人可以驳回一条发现，但必须带证据：量到的数，或标准里允许这样做的条款。驳回记在这一轮的记录里，下一轮评委看得到驳回的理由，不同意可以再提。再提的进给用户的清单，不再由修的一方单方面驳回。

### 3.5 分数靠不靠得住

开始改之前先做校准。校准用 16 张图：基准图 1 张，现在的真实界面 5 张（好的差的都有，包括修复前的模型面板），故意弄坏的 10 张。弄坏是在截图的浏览器页面里往基准界面上注入一处已知的毛病，不改仓库代码，清单在 `test/ui-polish/mutations.ts`：右边被裁、输入框盖住消息、正文对比度不够（这三个应判 P0）；一行错位 6px、渐变加阴影的按钮、右栏行距减半、两个主按钮（应判 P1）；11px 的字、用“·”拼接、圆角不一致（应判 P2）。

每家评委把这 16 张各评 3 次，每次都是新会话。批大小也在校准里测：14 张一批和 28 张一批各做一遍，不够一批的用别的真实界面凑满，凑数的图不算门槛。四条门槛都过才开始改：

| 门槛 | 数 |
| --- | --- |
| 复评稳定 | 同一张图同一项 3 次评分最大差不超过 1 分的图，至少占 90% |
| 拉得开分 | 基准图的页面分比 P0、P1 的弄坏图至少高 3 分，比 P2 的弄坏图至少高 1 分 |
| 抓得到 | 每个弄坏 3 次里至少 2 次被指出（框盖住弄坏的位置、记在预期的项、不轻于预期的严重度）；P0、P1 的弄坏至少 90% 被抓到 |
| 两家一致 | 两家页面分差不超过 1 分的图至少占 80%；基准图上没有任何一家提 P0、P1 |

正式评审用过了门槛的最大一档批大小（`score.ts` 的 `pickBatchSize`）。28 张过不了、14 张过了，就用 14 张一批，分波次串行跑，不加并发。

两档都没过，就把没过的那条对应的评分标准写细（补例子、把核对办法写具体），重做校准，最多 3 次。3 次还不过，把数据报给用户，由用户决定是放宽分数线还是换评委。

每轮评审里混进 3 张哨兵图（基准图和两张弄坏的），评委不知道哪些是哨兵。哨兵的分和校准时差得超过 1 分，这一次评审作废重评。

### 3.6 停止和回退

- 达标：同一个提交上连续 2 次独立评审，全部 133 张图页面分都不低于 9。第一次全部达标后不改代码，再评一次确认。
- 轮数上限：最多修 6 轮。
- 没进展：连续 2 轮不达标的图数没减少，并且最低页面分没升高。
- 到上限或没进展时停下来，把剩下的发现、两家的分歧、被驳回后又被再提的发现列给用户定。

一处修改留不留：归因把发现按根因分成组，一组一个提交。下一轮全量重评后，如果某张图出现了上一轮没有的 P0 到 P2 发现，算变坏。只是 P3 多了少了不算，那是评委的正常波动。变坏的图对应到改过它用到的文件的那个提交，整个提交撤回，这一组留到下一轮换个改法。目标界面没有变好的组也撤回。

这里和项目经理的设计有一点不同。原话是“目标界面分数上升、别的界面都不下降才留下”。按字面做，评委在别的图上多挑出一条 P3 就会让一处好的修改被撤回。所以“下降”定成出现新的 P0 到 P2 发现。

### 3.7 记录放哪

- 进仓库的：`docs/ui-polish/baseline/`（基准图和风格说明）、`docs/ui-polish/calibration.md`（校准数据）、`docs/ui-polish/rounds/<轮次>.json`（这一轮的提交号、每张图的 sha256 和分数、全部发现、修改分组和去留、PR）、`docs/ui-polish/rounds.md`（一轮一行的总表，加每张图各轮的分数）。它们跟这一轮的修改在同一个 PR 里。
- 不进仓库的：截图。一轮 133 张 2 倍图约 40MB。同一个提交重截出来逐字节一样，记录里有提交号和 sha256，要看哪一轮的图，检出那个提交跑一遍命令就有。当轮的图和评分卡在 `/tmp/fusa-ui-polish/<轮次>/`，Worker 和评委都读写得到。
- 给用户看的：每轮生成一个单文件 HTML（`pnpm ui:polish report`），每张图带发现的框、两家的分数、和上一轮的并排对比。每轮结束时项目经理把 `/tmp/fusa-ui-polish/<轮次>/` 复制到 `~/.agent-hub/pm-notes/ui-polish-loop/rounds/` 留底，因为 Worker 写不了那个目录。

### 3.8 命令

`pnpm ui:polish <命令>`，入口 `test/ui-polish/cli.ts`：

| 命令 | 做什么 |
| --- | --- |
| `inventory` | 打印界面清单 |
| `shots [--round R01] [--only 区域或界面] [--verify]` | 截全部界面并做机器检查；`--verify` 截两遍，有一张字节不同就失败 |
| `calibrate-shots` | 截校准用的 16 张 |
| `brief --round R01 --judge 厂商/模型 --batch 3` | 打印这一批的评委任务说明 |
| `check-cards --round R01 --judge 厂商/模型` | 评委自查评分卡格式 |

评委步骤的任务说明只有一句：跑 `pnpm ui:polish brief …`，照输出做。提示词因此只在 `judge-prompt.ts` 一处。

### 3.9 一轮怎么排成任务图

校准是一张单独的图，只跑一次（不过才重跑）：

1. `calib-shots`：Claude `sonnet`，跑 `calibrate-shots`。
2. 评委步骤共 18 个。28 张一批的那一档，16 张加 12 张凑数的正好一批，两家各评 3 次是 6 个步骤。14 张一批的那一档，16 张分成两批、各凑到 14 张，两家各评 3 次是 12 个步骤。18 个步骤排成 3 个波次，每波 6 个，后一波依赖前一波。
3. `calib-report`：Claude `fable`，跑 `calibration`，写 `docs/ui-polish/calibration.md`。这一步标 `confirm: true`，校准数据给用户看过再开始改。

每一轮是一张图：

1. `shots`：Claude `sonnet`。`pnpm build`，`pnpm ui:polish shots --round R<n> --verify`。
2. `judge-a-1` 到 `judge-a-5`：Antigravity `gemini-4-carbon`，各评一批 28 张。派之前用 `hub models --vendor agy` 核对模型 ID。
3. `judge-b-1` 到 `judge-b-5`：Claude Code `opus`，同上。两家的分批顺序不同，抵消先后次序的影响。

   10 个评委步骤排成两个波次，同时在跑的不超过 6 个：第一波是两家的第 1 到 3 批，依赖 `shots`；第二波是两家的第 4、5 批，依赖第一波的 6 个步骤。波次由 `screens.ts` 的 `judgeWaves` 算。校准定下来用 14 张一批时，每家 10 批、共 20 个步骤，4 个波次。
4. `triage`：Claude `fable`，依赖全部评委步骤。跑 `score`，把发现按根因分组（标准没写到的、共用组件的、单个界面的），写修改计划。全部达标时汇报“达标”，项目经理改派确认评审。
5. `fix`：Claude `fable`，接 `triage` 的工作目录。先补 `docs/ui-standard.md`，再修共用组件，最后修单个界面，一组一个提交。自己重截看效果，不自己打分。提 PR。
6. `review`：只在修改碰到审查红线时加（界面修改一般是纯展示，靠下一轮全量重评兜底）。

评委步骤不标只读。只读 Worker 只能写自己的临时目录，评分卡写不到 `/tmp/fusa-ui-polish/` 里。评委的任务说明里写明只看图、不读代码、不改仓库。评委用不着自己的 worktree，但并行步骤默认各开一个并跑一次准备命令（实测 29 秒）。任务图的步骤能不能不开 worktree，实现时确认；不能的话每个评委多等半分钟，不影响结果。

PR 合了之后项目经理建下一轮的图。下一轮的 `shots` 截的是合并后的 main。

评委用 Worker 而不用脚本直接调 `claude -p`、`agy`：Worker 的沙箱会遮住凭据目录，在 Worker 里再起一层厂商命令行多半登录不上；走任务图，额度用完、厂商没登录这些情况系统已经会处理。

## 4. 性能

循环不进产品运行时，不加缓存、状态快照和会长大的列表。按规矩里的 4 件事逐条答：

1. 失效：没有缓存。每次截图开头清空 `/tmp/fusa-ui-shots` 重灌种子。
2. 上限：会变多的只有记录。一轮一份 JSON，最多 `MAX_FIX_ROUNDS` 轮加校准和确认，十几个文件。一张评分卡最多 `MAX_FINDINGS_PER_CARD` 条发现，每条文字最多 `FINDING_TEXT_MAX_CHARS` 字，所以一轮的 JSON 最大约 133 × 20 × 2 条发现，实际预计几百条、几百 KB。`/tmp/fusa-ui-polish/` 每轮约 40MB，项目经理留底后可以删。
3. 前端引用稳定：不涉及，不改 `src/web`。
4. 验证：不涉及产品性能。循环自己的数（截图时间、评审时间、用量）在校准后写进 `docs/ui-polish/calibration.md`。

这些数只管循环自己，放在 `test/ui-polish/limits.ts`，不进 `src/shared/limits.ts`（同 `test/eval/limits.ts` 的做法）：

| 常量 | 值 | 怎么来的 |
| --- | --- | --- |
| `PASS_SCORE` | 9 | 用户原话 |
| `PASS_STREAK` | 2 | 项目经理定的“连续两次” |
| `MAX_FIX_ROUNDS` | 6 | 一轮 3 到 5 小时，6 轮约两个工作日 |
| `STALL_ROUNDS` | 2 | 一轮没进展可能是评委波动，两轮才算 |
| `CALIBRATION_RUNS` | 3 | 项目经理定的“同一张图评 3 次” |
| `CALIBRATION_MAX_SPREAD` | 1 | 项目经理定的“波动超过 1 分，9 分这条线没有意义” |
| `JUDGE_BATCH_CANDIDATES` | 14、28 | 校准时两档都测，用过了门槛的最大一档 |
| `JUDGE_MAX_CONCURRENT` | 6 | 项目经理定的，这台 Mac 吃紧 |
| `JUDGE_MAX_WORKERS_PER_REVIEW` | 10 | 项目经理定的；136 张每批 28 张是每家 5 个 |
| `MAX_FINDINGS_PER_CARD` | 20 | 一张图超过 20 条多半是把一个问题拆碎了 |
| `FINDING_MATCH_IOU` | 0.3 | 两家框同一处时框的大小常差一倍，0.3 能并上 |

## 5. 统一

- 厂商：循环里没有按厂商写的代码。评委是 `<厂商>/<模型>` 一个字符串，由任务图步骤的 `vendor`、`model` 指定。厂商名单仍以 `src/shared/vendors.ts` 为准。以后加一家新厂商当评委，不用改 `test/ui-polish/` 的任何文件，建图时换个 `vendor` 就行。隔离守护进程把各家命令都指到不存在的路径，用的是 `VENDOR_LIST` 的 `cli.envVar`，名单加一家自动跟上。
- 平台：评的是网页，三个平台看到的是同一份 `src/web`。截图只在 macOS 上跑，因为界面用系统字体，换平台字形就变，分数不能比。`capture.ts` 不写平台分支，在别的平台上能跑但出的图不拿来评分。Windows 和 Linux 上的原生外壳不在范围里。
- 界面清单、评分标准、补丁、弄坏、可调的数各只有一处定义（见第 7 节），截图、评委说明、合分、报告都从那一处读。
