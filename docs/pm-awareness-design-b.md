## 2. Current state and history

### Design history

The original Task Graph design assumed that a graph was the plan: dependency edges released work and the written nodes covered what remained. The draft at `7acebe9a:docs/task-graph-design.md` even described automatic completion after done or skipped nodes. The current [Task Graph design](task-graph-design.md) requires an explicit PM delivery; a graph can remain active when all its nodes are done. The review protocol later moved toward a small project neutral contract (`b2228357`), with repository policy outside the product. The product cannot infer a project's unwritten delivery policy from that contract.

The older handover design at `3437df1f^:docs/background-handover-design.md` keeps conversation text and Worker report references after a cut and moves held inputs forward. That protects conversation continuity. It has no way to represent an unfinished PM action. `0542ebcd` made a vendor switch reuse the current generation's recorded context rather than ask the old vendor to write a new summary; a ready renewal can still be reused. `594fd096` added quiescence and session ownership checks. `966cdcd8` added stale notice checks before a send and a driver write. `265f82e4` distinguished system input from user speech and recorded when the driver took it. Those fixes address transport and history. A taken message still does not mean the PM completed the work described in it.

### Ownership today

| Fact | Authoritative writer | Where it is repeated or missing |
| --- | --- | --- |
| Graph nodes, dependencies, and artifacts | Graph ledger through Worker report settlement, graph commands, and decision handling | `hub status`, graph details, handover, and the web compare or format overlapping facts. Graph status is active, completed, or cancelled. Node status is pending, running, waiting, done, or cancelled. A skipped node is settled, with a separate skipped flag. |
| Current PM generation and message delivery | Handover, sessions, and the message ledger | The handover text records historical discussion. The preamble adds a live graph section. A send action, its message row, and its taken stamp describe transport. They do not describe whether the graph still needs acceptance. |
| Review and external outcomes | Accepted review reports and the code host; repository rules determine what they mean | A prior review or green check can describe a different revision. The PM owns the missing wait and acceptance decision, often in chat or a shell. |
| Worker resources | The Worker and action ledgers own launch and exit; no ledger owner for the scarce resource | A handwritten queue and status words in a title repeat a state the product does not model. The action executor's concurrency of four limits action handlers, not simultaneous UI use. |

The missing concepts are a current PM responsibility derived from the graph and its declared delivery rules, and a resource claim rooted in the Worker launch lifecycle. Neither needs a new conversation service.

## 3. Reference designs and approach comparison

### Reference designs

| Product | Useful mechanism | Boundary for Bellwood |
| --- | --- | --- |
| [Temporal Workflow message passing](https://docs.temporal.io/encyclopedia/workflow-message-passing) | It separates a durable asynchronous signal, a query of current state, and an acknowledged update. | A notice can signal the PM; a query shows unresolved work; the action that resolves work updates the graph. Bellwood already has SQLite and turn receipts, so it does not need workflow replay. |
| [GitHub required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks) | Status checks target the latest relevant commit. A passing check on a different revision cannot satisfy the gate. | Bind evidence to a declared target and current revision. The code host is a source of evidence when a project uses one. It does not define Bellwood's default workflow. |
| [Argo Workflows synchronization](https://argo-workflows.readthedocs.io/en/release-4.0/synchronization/) | It distinguishes workflow parallelism from a shared semaphore, with explicit holders and waiters. | Use a resource key and a queue at admission. Start with one named local resource per request to avoid partial claims and cross-resource deadlocks. |

### Candidate structures

| Shape | How it works | Why choose or reject |
| --- | --- | --- |
| Prompt and tooling patch | Put a checklist in each PM turn, show more in every handover, and ask PMs to run a wait command and maintain a same-machine queue. | Small change. It leaves delivery and slot decisions scattered across prompts, agent memory, and command output. The title can still lie and two concurrent starts can still succeed. |
| Ledger facts and one dispatch gate (recommended) | Derive outstanding PM work and graph readiness from authored requirements, current evidence, existing graph/Worker rows, and resource requests. Use the existing notice path to signal a transition. Claim a slot at the Worker boundary. | Gives consumers one definition without rewriting conversations, graph execution, or vendor drivers. It needs schema and lifecycle work for evidence and resource claims. |
| Workflow runtime (day-one design) | A project coordinator owns durable inputs, workflow steps, timers, claims, and workflow state. Vendor sessions become execution clients. | Clean if starting with no graph, ledger, or action executor. For Bellwood it would replace existing graph and turn transactions and require replay/backfill across active projects. Its extra durability brings little for these incidents once the existing ledger owns the missing facts. |

### Recommended contracts

**One read of active work.** Extend the PM form of `hub status` (structured output and short text) and its graph overview source. Show actionable work first, followed by waiting conditions and active Workers, including standalone Workers. Reuse the graph state in the Work panel and in the first input of a successor. Include graph/step IDs, counts, Worker IDs and live phases, and the latest resolved gate or the outstanding gate. Keep existing detailed commands for inspection. The graph status is derived; a PM reading it, a model taking a notice, and a user viewing a card do not change it.

**Separate step progress, delivery evidence, and delivery.** A project can opt into a small reusable list of required evidence kinds and graph authors can add requirements. Save the resolved declaration at graph creation. A configuration edit affects new graphs; an active graph can bind or add a requirement with an explicit patch. A normal graph patch cannot drop a required policy entry. If the project allows a waiver, record the authorized decision under its existing checkpoint rules. In a project with a two-track policy, a graph missing the second declared evidence slot shows `2/2 steps · Review evidence missing` and points to the required role. Add or bind the missing review using the existing graph path. A matched review must PASS for the correct artifact and current target; a skipped step or arbitrary text cannot satisfy it. A follow-up target change invalidates old evidence unless the project's existing authorized review mechanism explicitly attests the new target. A graph without configured requirements goes directly to `Needs acceptance` once its declared steps settle. Only the existing `graph finish` transaction closes it, produces the delivery report, and clears acceptance. It reuses the same readiness requirement check. Preserve existing conditional open PR protections; `--unmerged-ok` does not waive an explicitly declared requirement. The design adds no auto-merge or automatic policy inference.

**External waits live with the graph.** Represent a wait as a declared evidence condition, with an immutable attempt ID and a stable target identity. For CI, the supported integration must record the exact repository or equivalent namespace, change identifier, revision, and requested checks. A newer revision stops the old attempt; recheck the target at acceptance. A cloud read cannot mutate a graph in the same transaction that does network I/O: the observer publishes a result only if the ledger still has that attempt and target. Use the existing durable action executor for read-only observation where a connector exists. Persist its next due time, deadline and result on the attempt. A daemon restart resumes due observations. An unavailable integration, stale head, timeout, or auth failure is visible work for the PM and never produces a synthetic PASS. For a project without a supported connector, use an existing Worker step or the PM checkpoint from friction PR-3 to attach current evidence; when the project uses a command, put its foreground wait in that Worker step. The existing Worker report or failure then causes a ledger transition. The daemon does not run arbitrary repository commands, and generic task graphs do not require CI. Friction PR-2's `worker wait` continues to answer Worker start/settle questions; it is not the durable source of external completion.

**Notice currency comes from the same read.** Once progress, a checkpoint, or an external observation makes work actionable, enqueue the typed notice via friction PR-4's `enqueuePmNoticeIn` in the same transaction as the transition. Use a stable subject, transition identity, and message ID. Reuse the message queue for delivery and the pre-write currency check on both sides of the driver boundary. Suppress stale, cancelled, or superseded notices before write. Keep taken notices as immutable history; hydration of a successor's pending work does not rewrite them. Coalesce repeated attempts for the same subject; never notify again just because the PM sent another message. Preserve D2: a passed user checkpoint wakes the PM within one minute and includes the user's note if that branch has no successor, even if an unrelated branch is active. If it makes the whole graph actionable, one notice carries both facts. If the next step starts or waits automatically for a resource, let the Work panel show that without a separate ordinary-pass wake.

**Admission belongs to the Worker boundary.** A declared step resource, or a PM-authorized standalone request, resolves to a resource key on the destination device. A bound step's resource demand is inherited by manual start, auto-dispatch, retry, and takeover; there is no force bypass. Device capacity is owner-configured. The Bellwood repository would declare a one-slot resource for real environment reviews; a project that does not declare one keeps current concurrency. One shared admission operation allocates a ticket and conditionally claims capacity before it can enqueue setup or launch. Only eligible tickets participate in FIFO. Dependencies and user approvals must clear first. A provisional Worker created for an existing approval flow cannot start before admission. When full, the graph and `hub status` show a real wait with no running process. A stable step title names the work. Releasing a slot grants the oldest eligible request; it does not require a PM turn. Logic reviews without that resource can still run.

Keep the claim across setup, a running turn, and parked or background work until the Worker and its relevant setup/child processes are confirmed quiescent. A report alone, or a failed process scan, cannot release it. Cancellation removes a waiting ticket immediately. Cancellation of a holder starts shutdown; it releases only after exit/reap. Takeover can replace the lease after the predecessor stops, never while both can run. If an operator lowers capacity, keep current holders and grant no new work until usage is below the new limit. Restart reaps or reconciles every holder before admitting waiters. A failed cleanup shows a blocked resource with the holder, rather than a timer that frees an unsafe slot.

The authority is the daemon on the execution device; the PM's browser and the Feishu hub do not admit work. A resource declared for a shared desktop must also have a common lock for daemon data directories that share that desktop. Reuse the process identity and atomic publication pattern from `src/daemon/store/lock.ts`, with an owner-protected namespace independent of the data directory. That file's stale-owner rule is insufficient for this lease. Persist the candidate claim ID first, acquire the platform lock outside SQLite, then confirm that claim ID in a new transaction before launching. Recovery reconciles the same ID on both sides of that boundary and quarantines an unprovable holder. Cross-project FIFO is scoped to one daemon authority; a second authority using the same desktop sees the external holder, not an invented queue position. Independent testbeds and devices have independent locks. The guard applies to declared work; it cannot classify an arbitrary command or stop a manually launched desktop tool.

### If graph readiness and handover coincide

| Ordering | Result |
| --- | --- |
| The notice is queued when the switch commits | Move the same message ID to the successor in the existing switch transaction. The old send action fails ownership; a still-current notice can be taken once by the new session. |
| The old driver took it before the switch | Keep that message on the old turn. The unresolved acceptance is still visible. Include it in the fresh opening brief. If it would otherwise have no input to open the successor, enqueue one successor attention notice through the same path, deduped by handover ID. Do not resend individual taken notices. |
| Readiness arrives after the switch | Enqueue for the current successor generation. The first input and notice use the same live ledger projection; pending notices already represented in that opening should be shown once in the rendered brief. |
| The graph is patched, delivered, or cancelled during the switch | Recheck the subject and attempt before driver write, retire invalid queued notices, and omit cleared work from the opening list. Preserve historical content. |
| The predecessor is still working, the switch is abandoned, or the daemon restarts | Existing quiescence and ownership rules choose the session that can receive pending inputs. Recover by message ID and graph/attempt state. A taken event is not an acknowledgement of the graph; a stale process event cannot finish a newer attempt. |

The guarantee is one logical current action, with idempotent acceptance and a durable notice that can be retried. A driver can die after reading input and before recording its receipt; model execution is not exactly once. The next generation sees which action remains. No follow-up uses the recorded chat as a second queue.

### Design red flags

The prompt patch has split ownership, a hand-synced queue and multiple ways to decide the same outcome. A full runtime makes the graph and new engine competing writers until the migration replaces all callers; launching it on the side would preserve that split. The recommended design keeps one operation that admits Workers and one operation that builds the active work projection. CLI output, web labels, and notices adapt the typed result. They do not load, validate and save it in separate layers or import SQLite row shapes. Read-only connector calls return observations; they cannot write gate state. There is one mapping of evidence kinds, one resource queue, and one sender. Keep internal queries private, remove forwarding methods without an adaptation, and derive renderer mappings from the shared union. The foundation remains usable; the missing responsibilities have owners without a ledger replacement.

## 4. Performance and bounds

Read active graph and resource views through indexes on PM, graph, and resource ticket. Avoid scanning messages, step logs, or ended Workers to build ordinary status output. Store at most one current attempt per requirement and one active ticket per requesting step or standalone Worker attempt. A report links to the existing result; it does not copy its transcript. Once an attempt or ticket settles, keep any audit reference with its graph or Worker under their existing age and count retention. If a growing table survives its owner, register and test its own age and count bounds before introducing it. Never silently purge live unresolved work. On capacity pressure, reject the new registration with a clear limit and preserve existing work.

No new long-lived cache. Read the snapshot after the committing transaction, and invalidate or notify on every transition, lease change, or policy patch. Dispose observations and listeners on shutdown and when the attempt ends. In the web, use the existing memoized selectors and return stable references while a snapshot is unchanged. Key any check retries to the attempt; errors use bounded backoff, not a cached pass. Keep output paged and compress large web responses.

| Proposed shared limit | Initial value and sizing |
| --- | --- |
| `PM_ACTIVE_WORK_PAGE_ROWS` | 32; 300 Worker records would occupy 10 pages if they were live, while finished Workers stay in their existing history. Include exact omitted counts and a stable continuation. Use the existing 8,000-character handover graph budget as a hard cap, with a short overflow line and the status command. |
| `GRAPH_DELIVERY_REQUIREMENTS_MAX` | 16 per graph, half the existing 32-node graph cap. Bound source references, labels, and outcomes with the graph spec and text caps. |
| `DEVICE_ACTIVE_RESOURCE_REQUESTS_MAX` | 300 across the authority. Sized for the site's month of 300 Worker completions even if that many resource requests accumulate without a release. Admission fails before launch when full; a waiting node shows the reason. Reuse the ticket count cap for each resource index page, with paged output. |
| `DEVICE_ACTIVE_EXTERNAL_WAITS_MAX` | 300 across the authority, one active attempt per declaration and up to one month's Worker completions outstanding. Reuse the action executor's existing concurrency limit and use bounded retry scheduling and deadline per integration. Past attempts do not enter the due queue. |

At 30,000 messages and 50,000 step logs, the indexed read still touches the live work page and its bounded references. Verify this with the repository's month-size fixture plus 7 active graphs and 6 active Workers, then a maximum-page fixture. Record before and after returned bytes, query plans, rows visited, update count during an unrelated Worker pulse, and repeatable timings using the benchmark checklist and blast radius skills at implementation review. Numbers here are sizing targets, not measurements.

Until the real environment verifies a platform's process identity and cleanup, that platform must report a blocked slot for an unverifiable holder. No permission or sandbox boundary changes are needed.
