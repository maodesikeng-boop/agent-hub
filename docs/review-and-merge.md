# Testing, review, and merge policy

Full verification, CI, independent review, and merge rules for this repository. Start with [`../AGENTS.md`](../AGENTS.md) for everyday engineering rules, [`../REVIEW.md`](../REVIEW.md) for path-triggered review checks, and [`plan-standard.md`](plan-standard.md) for design plans and acceptance evidence.

## Local verification

- **Regression tests for bug fixes.** For every bug fix, write a regression test or structural guard that reproduces the defect and confirm it fails before changing production code. Keep both the pre-fix failure output and the post-fix passing output for the report. When the test can run only on another platform in cloud CI (such as Linux `bwrap` or Windows native), push a test-only commit first to capture the red CI run, or record the pre-fix failure check as `not verified` with the reason and ask the Project Manager how to proceed.
- **Iterating.** While editing or fixing individual failures, run only the targeted test files or screenshot target affected by the change, such as `pnpm exec vitest run <file>` or `pnpm ui:polish shots --only <target>`. Do not chain `pnpm test:related`, full `pnpm ui:polish` runs, or performance benchmarks into repeated `&&` loops after each small edit.
- **Final local gate.** Run the full local gate once after all edits are final and right before the final push: `pnpm lint`, `pnpm typecheck`, `pnpm test:related`, and `pnpm verify` (`.agents/skills/verify/SKILL.md`). Do not edit files while any gate command is running, and never replace that final `pnpm test:related` pass with hand-picked test files. If you edit any file or merge `main` after the local gate starts, rerun all four commands from scratch rather than running a subset.
- **How `pnpm test:related` selects tests and bounds concurrency.** `scripts/test-related.ts` uses `scripts/related-graph.ts` (`oxc-parser` symbol-level static impact graph) to diff changed exports since the merge base with `origin/main`, traverse named and `export *` barrels plus Vitest project `setupFiles` at symbol granularity, treat runtime dynamic `import()` and `vi.mock`/`vi.doMock`/`vi.unmock`/`vi.importActual`/`vi.importMock` edges as fail-closed whole-file dependencies, bridge dynamic `src/vendors/<id>/{daemon,paths}.ts` loaders, link non-code runtime assets (migrations, workflows, fixtures) by path, and always include the tree-scanning guards in `ALWAYS_RUN_TESTS`. Changes to `package.json` or `pnpm-lock.yaml` stay scoped to tests and `scripts/` modules that reference them (plus `ALWAYS_RUN_TESTS`, including `src/direct-dependencies.test.ts`), leaving the full suite to CI. Changes to `vitest*.config.*`, `vite.config.*`, or `tsconfig*.json` fail closed to the full suite. Outside CI, `pnpm test:related` caps local Vitest forks to `clamp(floor(cpus / 2), 1, min(TEST_RELATED_LOCAL_MAX_WORKERS, selectedFiles))` unless overridden by CLI worker flags (`--maxWorkers`, `--no-file-parallelism`) or `BELLWOOD_TEST_MAX_WORKERS`. Pass `--dry-run` to list selected files without spawning Vitest and `--explain` to print causal symbol paths. Add any new guard that scans the tree instead of importing its target to `ALWAYS_RUN_TESTS`.
- **Mandatory extra checks.** Run `src/shared/write-scope.test.ts` whenever sandboxes or write scopes change. For changes touching Feishu, the mesh, the relay, or vendor drivers, also run `pnpm tester` on the resident test bench (`.agents/skills/tester/SKILL.md`).
- **Worker sandbox notes.** Inside a macOS Worker sandbox, tests that need `ps` or a nested `sandbox-exec` skip through `test/sandbox-probes.ts` and still run on CI. `pnpm test:related` ends by listing the test files that skipped this way, and `test/sandbox-probes.test.ts` fails a test that probes the nested sandbox on its own. Workers may disable a vendor CLI's built-in inner sandbox as needed (for example, Claude Code's `dangerouslyDisableSandbox`) when double sandboxing blocks a normal build or test command. Bellwood's outer OS sandbox stays active; never use an inner-sandbox toggle to read Bellwood's data directory (such as `state/`, ledger databases, credentials, or other sessions' files) or to bypass write-scope or permission boundaries. The project setup command installs dependencies outside the sandbox; running `pnpm install` inside the sandbox cannot write the shared pnpm store and builds a separate store of about 1 GB in the ignored `.pnpm-store/` directory, so rerun `pnpm install` only when `package.json` or `pnpm-lock.yaml` changed.
- **Flaky tests and local load failures.** Never use `gh run rerun` to hide a flaky test. When a test fails during local `pnpm test:related` and appears to be an intermittent failure caused by local machine load, do not dismiss it with a bare note that it passes in isolation. Record the exact failing test and error, rerun the failing file in isolation and record its command and passing output, and confirm a clean result from either a full `pnpm test:related` rerun (for example with lower concurrency such as `--maxWorkers=2`) or cloud CI via `node scripts/wait-checks.ts <PR>`. Report both the isolated rerun result and the full rerun or cloud CI result. If the failure repeats on rerun, fails in cloud CI, or lacks a passing full rerun or cloud CI result, report it as a problem instead of reporting done.

## Cloud checks and handoff

- **Opening PRs.** For tasks with a design plan, the Project Manager opens a draft PR (`gh pr create --draft`) after the plan is pushed, subsequent implementation and fix steps push to that same branch, and the Project Manager marks the PR ready (`gh pr ready`) once ready for review and any required user decision is approved. Open non-plan PRs ready for review. When a Worker has GitHub access and the task asks it to open the PR, the Worker opens it; when a Worker lacks GitHub access or the task leaves PR creation to the Project Manager, the Project Manager opens the PR after the Worker pushes.
- **Required PR checks.** Cloud CI runs `migration-claims` on every PR to `main`, alongside the 4 parallel Ubuntu full-suite shards (`check (ubuntu 1/4)` through `check (ubuntu 4/4)`), `verify-smoke (ubuntu)`, and any path-filtered platform jobs as the hard merge gate.
- **Handoff division.** Implementation Workers push to the branch and hand off right away so parallel review and cloud CI run together. Exception: when a PR touches platform code that this machine cannot test (Linux `bwrap`, Windows native, or desktop packaging), when the final `pnpm test:related` lists test files that the sandbox made skip, or when the PR has no immediately following review step, wait for the PR's CI checks before reporting done. When that wait exception applies and no PR exists yet because the Worker lacks GitHub access (or the task assigns PR creation to the Project Manager), push the branch and report a problem asking the Project Manager to open the PR. After the Project Manager opens the PR and replies with the PR number, run `node scripts/wait-checks.ts <PR>` in the same session and report done only after all required cloud checks pass.
- **Waiting for CI.** Use `node scripts/wait-checks.ts <PR>` (or `node scripts/wait-checks.ts` on the PR branch; `check` takes about 3 minutes). Do not use `gh pr checks --watch`: it hangs on `bellwood/review` (which stays pending until independent review passes on high-risk paths) and on merge conflicts where `pull_request` workflows never start. `scripts/wait-checks.ts` ignores pending `bellwood/review`, fails immediately on merge conflicts, a GitHub `BEHIND` verdict, or red checks, and rechecks migration claims against current `main` and open PRs before reporting green.
- **Red checks.** A red check is yours to fix, including Linux `bwrap` and Windows jobs this machine cannot run. If the same failure is red on `main` or the test is flaky, report it as a problem instead of reporting done.
- **Layered cloud workflows.** `check` (4 Ubuntu shards) runs on every pull request with no path filter so branch protection can require `check (ubuntu 1/4)` through `check (ubuntu 4/4)`. Touching platform code, drivers, process, pipe, git, or sync layers, `apps/windows/**`, or `test/windows/**` also triggers `.github/workflows/windows.yml`. Touching `apps/**`, packaging scripts, or `pnpm-lock.yaml` triggers the desktop installer workflows. Runs on `main` are never cancelled by a later merge. `.github/workflows/nightly.yml` runs the full suite on Ubuntu, Windows, and macOS against `main` at 14:17 UTC (22:17 Beijing time, off the top of the hour) every night to surface flaky tests. Release candidate tags run the same three suites (`check.yml`, `windows.yml`, `macos.yml`) plus `pnpm verify` on the tagged commit before `.github/workflows/release.yml` publishes anything ([Release flow](release-flow-design.md#releasing)). `scripts/ci-workflows.test.ts` guards these rules and the desktop path filters.

## Independent review

Each review round runs two tracks in parallel. PRs that change only documentation and repository rules run only the logic review track.

### Logic review

Start with the pre-review checks in `REVIEW.md` on `main` (`git show origin/main:REVIEW.md`, "Before you review"): confirm that `HEAD` matches the PR head commit and the working tree is clean, and stop with a problem marked `not reviewable` or `unable to review` (never `FAIL`) if either check fails. Then inspect the PR diff and surrounding code against the general checklist in `src/shared/review.ts` and every rule in `REVIEW.md` on `main` whose `Trigger:` matches a changed path. Logic review runs on a different vendor from the implementation step. During review, run only the directly related test files (or `pnpm test:related --base <prev-sha>` on a follow-up round) and `pnpm verify`, plus real-browser render checks when UI files changed. Whenever a PR exists, run `node scripts/wait-checks.ts <PR>` before issuing a verdict and do not rerun the full `pnpm test:related` locally. Run full `pnpm test:related` locally during review only for branches without a PR or CI run.

### Real-environment review

Run every acceptance scenario from the design plan end to end in a real environment under one evidence rule. Run at most one real-environment review on the local machine at a time.

- **Evidence rule.** Each scenario that runs must produce a screen recording (video) or a complete start-to-finish screenshot sequence (never a single static image). Only the listed unavailable cases below may instead record the scenario, the reason, and `not verified`, which does not count as verified or passing. A scenario with neither fails review.
- **Web flows.** Run web-only flows that do not depend on a missing real dependency locally against an isolated Bellwood instance with a separate temporary data directory and record them with Playwright. Those web-only flows cannot claim `not verified`. When a web scenario also depends on a missing real dependency (such as a real vendor CLI that cannot run safely isolated locally and cannot run on a testbed), the exception applies only to that missing dependency. Run the web portion that can execute in the isolated local instance with a Playwright recording or start-to-finish screenshot sequence, and record only the missing real-dependency portion with the scenario, the reason, and `not verified`.
- **Real vendor CLIs.** Prove vendor CLI behavior on this track by running against the real vendor CLI (locally or on a dedicated testbed). Hand-written fake events and fake CLIs serve only as automated regression tests and cannot prove vendor behavior on their own. Before running a real CLI locally, verify that the isolated instance cannot alter the user's own vendor config. If safe isolation is not verified or the vendor CLI is unavailable locally, run the scenario on a dedicated testbed when available. Only when the vendor CLI cannot run safely isolated locally and cannot run on a testbed either, record the missing real-CLI portion with the scenario, the reason, and `not verified` until a dedicated testbed is ready.
- **Prompt-cache preservation (hard gate).** Prompt-cache preservation is a separate hard gate that the real-CLI exception cannot waive. When a change touches session prompts, messages, tools, or MCP definitions, compare before and after `TokenUsage.cacheRead` from real sessions for every affected vendor under comparable conditions (same vendor, same model, comparable session and warm-up), running on the testbed if unavailable locally. Only when an affected vendor cannot run either locally or on the testbed, mark that vendor `not verified` and have the Project Manager escalate to the user with a decision card for that vendor. Without explicit user approval for that vendor, review judges `FAIL` and blocks merge. If the user approves proceeding without that vendor's comparison, record the decision card ID and the user's exact quote in the PR body. Once review verifies that recorded approval, review does not judge `FAIL` for that unavailable vendor's missing comparison. If a measured real-session comparison shows `TokenUsage.cacheRead` regressed, review always judges `FAIL` and blocks merge regardless of any approval.
- **Feishu, mesh, and desktop flows.** Run Feishu, multi-computer mesh, and desktop app flows on the testbed or with Computer Use, or record the scenario, the reason, and `not verified` when neither is available locally.

### Aggregation and rounds

Tag each finding in the report's `问题` field as `[Important]`, `[Nit]`, or `[Pre-existing]`. Only `[Important]` results in `FAIL`, while `[Nit]` and `[Pre-existing]` are noted with `PASS`. Wait for both parallel tracks to finish before aggregating results: even if one track reports `FAIL` first, wait for the other so all findings go into one fix step. One review round equals one run of each track. Round 2+ follow-up reviews verify open `[Important]` findings and the incremental diff since the last reviewed commit. After 3 rounds with an open `[Important]` finding, stop and have the Project Manager escalate to the user with a decision card.

### Updating tests and `REVIEW.md`

Keep per-PR regression fixes, second-occurrence `REVIEW.md` rules, and the nightly review pass separate:

- **Every `[Important]` fix (both tracks).** When fixing any `[Important]` finding from either logic review or real-environment review, add a reproducing regression test or structural guard in the same PR. When a real-environment finding exposes a recurring class of missing scenarios, also add that class to the scenario categories in `docs/plan-standard.md` or to the testbed script.
- **Second occurrence (`REVIEW.md` rule).** Prefer an automated test or lint rule over a `REVIEW.md` entry. Add a `Trigger:`, `Check:`, and `Seen in:` entry to `REVIEW.md` (keeping existing entries) only when the same mistake can be spotted only by reading a diff and has recurred in at least 2 PRs. When the Project Manager spots a second occurrence during development, the Project Manager instructs that PR's fix step to add the test or `REVIEW.md` rule directly and logs it on the scheduled list so the nightly job does not add a duplicate.
- **Nightly review pass (00:00).** The nightly 00:00 scheduled review job classifies `[Important]` findings from both review tracks over the prior day and adds a regression test or `REVIEW.md` rule once a recurring mistake reaches 2 PRs, skipping items already logged on the scheduled list.

## Merging and post-merge

- **Branch protection.** `main` is protected. Merge only through a pull request whose checks have all finished green, including path-filtered Windows and desktop jobs that ran, and after required reviews pass. Use squash merge only; GitHub deletes the head branch after merge. Never push directly to `main`, and never merge a draft.
- **Hard gates.** A PR with an unresolved hard gate (such as an affected vendor whose prompt-cache comparison cannot run either locally or on the testbed and is `not verified`) cannot merge unless the Project Manager escalates to the user with a decision card for that vendor, receives explicit user approval, and records the decision card ID and the user's exact quote in the PR body. A measured `TokenUsage.cacheRead` regression always fails review and blocks merge regardless of any approval.
- **Review stamp for high-risk paths.** For a PR that changes a path listed under "Paths that require a review stamp" in `REVIEW.md`, once both independent review tracks judge `PASS` on its head commit (or logic review judges `PASS` for PRs that change only documentation and repository rules) and cloud checks are green, the Project Manager posts the required `bellwood/review` `success` commit status with `node scripts/post-review-stamp.ts <PR> --sha <HEAD_SHA> [--account <login>]` (for example `--account maodesikeng-boop` when `gh`'s active account lacks write access) and then squash-merges without waiting for user approval to merge. If the gate carries a prior stamp under the clean merge rule in `REVIEW.md`, use that status for the new head.
- **Post-merge delivery.** After merging, the Project Manager delivers the acceptance evidence package to the conversation and Router: test results (pre-implementation baseline, post-implementation passing commands and outputs on HEAD, and cloud CI results) plus real-environment evidence (a video or start-to-finish screenshot sequence for each scenario that ran, never a single static screenshot, and a `not verified` record naming the scenario and reason for any listed case that could not run yet).
- **Task Graph and daemon reload.** A Task Graph line shares one PR, and the Project Manager runs `hub graph finish` only after that PR merges. When a merged PR changes the daemon or the web UI, the Project Manager runs `hub self-reload` (with `--build` when `src/web/` changed) so the running daemon serves the new code.

## Updating a PR description

To update a PR description, write the Markdown body to `<file>` and run:

```sh
git fetch origin main
git tag -f -a --cleanup=verbatim pr-body/<PR> -F <file> origin/main
git push -f origin refs/tags/pr-body/<PR>
```

`.github/workflows/pr-body.yml` applies the description to PR `<PR>` and removes the remote tag.
