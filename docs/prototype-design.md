## 1. 目标和范围

### 1.1 原型要证明什么

1. **一个人能用聊天软件的方式指挥一组 agent 干活**：在项目群里说一句话，项目经理拆活、派 Worker、验收，最后用户在群里和收件箱里看到带证据的结果，中间不用盯着。
2. **只跑官方、未修改的 `claude` 程序，也能把这套流程跑通**：守护进程不碰登录凭证，不经过 Agent SDK。
3. **无人看管时不丢东西**：守护进程重启、`claude` 崩溃、电脑睡眠之后，对话、工单、待办都还在，没做完的接着做。
4. **危险操作要用户点头**：合并、删除这类不可逆的动作要用户批准；agent 自己弹出的权限请求都转到收件箱，由用户在界面上批准或拒绝。原型不另做隔离，局限见第 11.3 节。
5. **总助分拣够用**：用户在总助那里随手丢的事，能落到对的项目、对的处理方式上；分错了能纠正。

### 1.2 原型不做什么

- 不做飞书、手机、远程连接、推送、GitHub 和邮件入口。
- 不做主动模式（agent 自己发现活来干）。
- 不做语音输入、头像生成（头像只支持上传图片或用名字首字生成默认头像）。
- 只接 Claude。Codex、Gemini 等只在驱动层留接口。
- 不以 T3 Code、OpenClaw 等现成平台为底座。
- 不做多用户、权限分级、云端部署。
- 不做桌面外壳。网页界面先在浏览器里打开。
- 不自动 `git push`、不开 PR、不部署。

### 1.3 试点

- agent-hub 自己。
- 用户的一个个人 TypeScript 项目（git 仓库、有测试、最近常改）。

两个试点项目都要是 git 仓库，Worker 才能在 worktree 里干活（见第 7.7 节）。

## 2. 角色

三个角色都是跑着的 `claude` 进程，区别在于启动时给的提示词、工作目录、允许的工具，以及守护进程怎么对待它的输出。

### 2.1 总助

**是什么**：一个入口。用户什么都能往这里丢；它负责分拣，再加每天一次汇总。总助没有长期会话，每次处理一条消息都现拼上下文、调一次模型，用完就丢。

**分拣分两步**（和 `HANDOVER.md` 第 2.2 节一致）：

1. **代码规则，不花 token**：
   - 消息以 `#项目名` 开头 → 直接定位到这个项目。
   - 用户在某个项目群里说话 → 不经过总助，直接给这个群（见第 2.2 节）。
   - 用户在项目群里 @ 某个 Worker → 直接给这个 Worker。
2. **调一次模型**：剩下的消息，总助拼一份上下文：自己的规矩、所有进行中项目的名片（名字、一句话说明、项目经理是谁）、各项目进行中的工单标题和状态、这个对话最近几条消息、新消息。让模型按固定格式回答“归哪个项目、怎么处理、理由、拿不准的程度”。

**选项目，不选人。** 选好项目后分四种处理：

| 判断 | 处理 | 用户看到 |
|---|---|---|
| 要讨论、规划、取舍 | 把消息转进这个项目的群，交给项目经理 | 总助回一句“转给了 X 项目”，带跳转链接；项目群里出现这条消息，标注“经总助转来” |
| 目标明确的小活 | 守护进程直接建工单、派 Worker，工单记在这个项目里；做完交项目经理验收 | 总助回一句“已在 X 项目建工单 #N”；项目群里出现工单卡片，项目经理收到一条通知 |
| 不用钻进项目就能答（问进度、排优先级、提醒、汇总） | 总助自己答，数据来自账本 | 总助直接回答 |
| 对不上任何项目 | 问用户 | 总助发一张卡片：几个最可能的项目按钮 + “新建项目” |

- 小活的判断要保守：这个项目里有进行中的工单可能碰到同一块东西时，转给项目经理，不自己派。
- “拿不准”时一律发卡片问，不猜。
- 每次分拣都写一条分拣记录：哪条消息、走的代码规则还是模型、去了哪、理由。用户点“分错了”改派，改派也记下来；同类错误攒多了，由用户决定要不要加成代码规则。
- 每条消息最多经过一次模型判断（`HANDOVER.md` 第 2.1 节）。

**每日汇总**：M6 先由项目经理做（用户要日报时用 `hub schedule add` 建，不默认建，见第 10 章）；总助的每日汇总（默认每天 9:00，数据来自账本，总助只负责写成人话）放到 M7 再说。内容都是昨天完成了什么 / 什么在等你 / 什么在进行 / 风险。

**参考**：
- 和 DeepSeek 原型一致的地方：一个常驻的分派者（DeepSeek 叫 Router，见其 Policy、MasterAssessor 两节）在前面接消息，再派给后面的执行者。不一致：DeepSeek 的 Router 有一个常驻主会话（main Session），我们的总助不留会话，每次现拼上下文。理由：用户来自不同项目的需求不多，常驻会话越聊越长，反而让分拣受旧对话影响。
- 和 Grok Bot 一致：有一个置顶的主 bot（Grok 叫 Primary Bot），平时的事先找它。不一致：Grok 的 Primary Bot 自己也干活、能主动接活；我们的总助只分拣和答简单问题，主动模式原型不做。

### 2.2 项目经理

**一个项目经理就是一个会话，管一个项目**（11-03 改）。

- 一个项目经理有：名字、头像、模式、性格设定（人设、做事习惯、跟用户相处的规矩）、自己的定时任务。这些存在软件的数据目录里。
- 每个项目经理只有一个会话（左栏一行），只管一个项目：一个主文件夹，加上可选的附加文件夹。要管另一个项目，就新建一个项目经理。不同的项目经理各自的会话可以同时跑。
- 还没有项目的项目经理（比如第一次启动自动建的那个），在数据目录下它自己的空文件夹里跑。
- ~~同一个项目经理管好几个项目、每个项目一个群、另有一个私聊；把项目交给别的项目经理~~：11-03 拿掉了。

**两种模式**，用户创建项目经理时选：

| 模式 | 写进提示词的默认做法 | 适合 |
|---|---|---|
| 只管理 | 只讨论、拆任务、派 Worker、验收，自己不改代码 | 复杂项目（推荐） |
| 自己也干活 | 自己直接在项目文件夹里改，不派 Worker | 低代码、不复杂的项目 |

- 模式只是提示词里的默认做法，程序不硬拦：“只管理”的项目经理照样有改文件的工具，用户直接让它自己做，它就自己做。
- 项目经理能改自己的做事习惯（包括改模式）：它通过系统命令改性格设定，守护进程写文件、留记录，并在聊天里发一行“项目经理改了自己的做事习惯：……”，用户能看到、能撤销。
- 安全红线不在性格设定里，项目经理改不了（见第 11 章）。

**在会话里怎么工作**：

1. 会话的工作目录是项目的主文件夹，其他挂着的文件夹用 `--add-dir` 加进来；这个项目所有 Worker 的 worktree 所在目录也加进来，方便验收时看改动。文件夹变了（建项目、挂、移除），下一条消息前自动 `--resume` 重启，聊过的都在。
2. 启动时读项目的 `AGENTS.md`。
3. 用户在会话里说话（没有 @ 别人）→ 交给项目经理。
4. 要派活时，用系统命令建工单（标题、目标、验收标准、建议用的模型），守护进程负责建 worktree、启动 Worker。
5. 收到 Worker 汇报 → 自己验收：看改动、跑测试、对照验收标准。不合格就打回，合格就提交给用户验收。
6. 需要用户拍板时，用系统命令发一张“等你处理”的卡片，进收件箱并弹通知。普通回复不弹通知。

**自然语言操作项目**：建项目（定主文件夹）、挂文件夹、移除文件夹、归档、删除都可以在会话里用一句话说，项目经理调系统命令执行，每一步都记录，具体见第 9 章。

**Worker（M3）**：Worker 的回复出现在项目经理的这个会话里，用户点开能看 Worker 的完整过程（第 3.3、3.4 节）。

**参考**：
- 和 Grok Bot 一致：每个 bot 有名字、头像、分工和自己的记忆，routine（定时任务）属于某一个 bot，一个 bot 一份对话（见 Grok 文档 Bots、Skills and routines 两页）。我们的项目经理多了“管一个项目”：会话在项目文件夹里跑。
- 和 DeepSeek 原型不一致：DeepSeek 没有“项目经理”这一层，Router 直接派 Worker。我们保留项目经理，是因为用户的主要工作方式是“跟一个懂项目的人讨论，再让它派活”（`HANDOVER.md` 第 2.1 节）。

### 2.3 Worker

- 一张工单一个 Worker，在自己的 git worktree 里干活，做完就散。
- 没有固定名字和头像，界面上显示成“Worker · 工单名”。
- 启动时只拿到：工单号、标题、目标、验收标准、项目的 `AGENTS.md`、汇报格式。需要更多背景时，它用系统命令按工单号读原始消息（`HANDOVER.md` 第 2.2 节第 3 条）。
- 最后一条回复必须按固定格式写汇报（第 8.4 节）。守护进程是它的父进程，直接从输出里读这条汇报。
- 中途有问题：在汇报里写“有问题”并结束这一轮；项目经理回答后，守护进程用同一个会话把回答发给它，它接着做。
- 用户可以在项目群里 @ 它，消息直接交给它（项目经理同时收到一份抄送）。
- 活是“派”的：由项目经理或总助指定，Worker 不从公共列表里自己领。

**参考**：
- 和 DeepSeek 原型一致：一张工单一个会话、一个目录；Worker 没有直接问人的工具，问题通过汇报交上去（DeepSeek 的 DshExecutor、Executor tools 两节）。
- 不一致：DeepSeek 的 Worker 通过六个专用工具和系统交互；我们的 Worker 主要靠最后一条回复交汇报，必要时用命令行（第 8 章）。理由：最后一条回复谁家 agent 都能写，不依赖某家的工具协议。

## 3. 界面

守护进程自带一个网页界面，只监听 `127.0.0.1`。样子参考 Grok Bot：聊天软件，左边是联系人，右边是对话。

> 11-03 改：没有项目群了。左栏只列项目经理，每人一行，点进去就是它唯一的那个会话；下面图里的“(群)”“＋项目”“项目群”现在都没有，图里群的那些内容（工单卡片、Worker 往来）以后出现在项目经理的会话里。

### 3.1 整体布局

```
┌──────────────────────┬─────────────────────────────────────────┐
│ 📥 收件箱        (3) │  项目群：agent-hub          成员 文件夹 ⚙ │
│ ★ 总助   早上的汇总… │─────────────────────────────────────────│
│──────────────────────│  [项目经理头像] 小林                      │
│ (头像) 小林          │  ┌────────────────────────────┐         │
│        好的，我先…   │  │ 我拆成两张工单……             │         │
│ (头像) 阿周          │  └────────────────────────────┘         │
│        已归档 …      │  ┌ 工单 #12 修复重启后丢消息 ────────┐   │
│──────────────────────│  │ 状态：进行中   Worker 在做   12 分钟 │   │
│ (群) agent-hub       │  └──────────────────────────────────┘   │
│      工单 #12 进行中 │  ⇅ Worker · 修复重启后丢消息 与 小林      │
│ (群) 另一个项目      │     6 条消息往来                 [展开]  │
│      …               │                ┌──────────────────────┐ │
│                      │                │ 用户的消息靠右        │ │
│──────────────────────│                └──────────────────────┘ │
│ ＋项目经理  ＋项目 ⚙ │  [输入框：@ 提到成员，# 指定项目]   [发送] │
└──────────────────────┴─────────────────────────────────────────┘
```

### 3.2 左栏

从上到下：

1. **收件箱**：固定在最上面，右边是“等你处理”的数量。
2. **总助**：置顶联系人，带星标。
3. **项目经理**：每人一行，头像、名字、最后一条消息、时间、未读数。有进行中的工单时，名字旁边显示一个小圆点。
4. ~~项目群~~：11-03 拿掉了。
5. **已归档**：折叠的一组，默认收起。
6. **左下角**：“新建项目经理”“设置”两个按钮（没有单独的“新建项目”）。

项目经理按最后一条消息的时间排序。

### 3.3 对话页（总助、项目经理通用）

- **顶栏**：名字；项目经理有项目时显示它的文件夹（主文件夹在前）；以后显示正在干活的 Worker；按钮：定时任务、设置。
- **消息**：用户的靠右；agent 的靠左，带头像和名字。系统消息（比如“已建工单 #12”“项目经理改了做事习惯”）居中显示成灰色小条。
- **agent 正在干活时**：消息流底部显示一行状态，比如“小林 正在运行 `npm test`”，旁边一个“停止”按钮。点“停止”会结束 agent 当前这一轮，会话保留，可以接着说（做法见第 7.4 节）。
- **工具调用**：一轮里 agent 读文件、跑命令这些操作，折叠成一行“执行了 7 个操作”，点开看每一步。
- **Worker 和项目经理的来回**：折叠成一行“⇅ Worker · 工单名 与 项目经理名，N 条消息往来”，点开按时间顺序看全部。
- **工单卡片**：标题、状态、谁在做、已用时间。按钮：“查看过程”（打开工单详情）、“停止”、“@它”。状态变了，卡片原地更新，不刷屏。
- **等你处理的卡片**：权限请求、项目经理的提问、审批（合并、归档等）都显示成卡片，带按钮；同一张卡片也出现在收件箱里，在哪边处理都行，处理后两边一起变成“已处理”。
- **输入框**：
  - 打 `@` 弹出成员列表，可选项目经理或某个 Worker。
  - 在总助那里打 `#` 弹出项目列表，选了就跳过分拣。
  - Enter 发送，Shift+Enter 换行。
  - 可以拖文件进来，文件存进数据目录，消息里带上路径给 agent。

**和 Grok Bot 的异同**：左边联系人 + 群、群里 @ 某个 bot，和 Grok 一致（Grok 文档 Chat and collaboration 页）。不一致：Grok 的审批卡片、登录请求不出现在群里，只在私聊里处理；我们直接在群里显示，因为原型只有用户一个人，没有群里泄露给别人的问题。Grok 的群成员是固定挑选的 2～6 个 bot；我们群里的 Worker 随工单进出。

### 3.4 工单详情（右侧滑出的面板）

- 标题、目标、验收标准、谁派的（项目经理或总助）、用的模型。
- 状态历史：每次状态变化的时间和原因。
- Worker 的完整过程：消息、操作、汇报原文。
- 改动：分支名、worktree 路径、改了哪些文件（`git diff --stat` 的结果），可以展开看具体改动。
- 证据：测试结果、截图、怎么验证的。
- 按钮：停止、打回（填理由）、通过、通过并合并（这个按钮就是合并的批准）。

### 3.5 收件箱

按 `HANDOVER.md` 第 2.4 节分四档，页面上是四个分组：

| 分组 | 放什么 | 每一条能做什么 |
|---|---|---|
| 等你处理 | 权限请求、审批（合并、归档、删除、建文件夹等）、项目经理的提问、需要你选项目、处理不了的故障（比如 `claude` 要重新登录、定时任务失败） | 按钮：允许一次 / 拒绝；或者选项按钮；故障类给出要做什么 |
| 待验收 | 项目经理验收通过、等你最后确认的工单 | 查看详情、通过、通过并合并、打回 |
| 进行中 | 所有进行中的工单和定时任务 | 只看，点进去跳到工单 |
| 定期汇总 | 每日汇总等定时任务的结果（M6：定时任务的结果就在项目经理的对话里） | 只看 |

每一条都标明来自哪个项目、哪个会话，点一下跳到对应的聊天位置。

### 3.6 其他页面

- **项目经理资料页**（点头像打开）：名字、头像（上传或默认）、模式、模型、性格设定（可以直接编辑，下面列出每次修改的记录，谁改的、改了什么、能撤销）、它的项目和文件夹、它的定时任务。
- **项目设置页**（会话顶栏的设置，以后做）：项目名、一句话说明、文件夹列表（加、删、设为主文件夹）、用哪个 Claude 配置目录（不同项目可以用不同账号登录，见第 7.1 节）、定时任务、归档、删除。不能换项目经理（11-03 拿掉了）。
- **新建项目经理**：名字、主文件夹（可选，填路径；不填以后在会话里说）、头像、模式（两个选项各带一句说明，“只管理”标“推荐用于复杂项目”）、模型、性格设定（给一份模板，可改）。
- ~~新建项目~~：11-03 拿掉了单独的入口，建项目经理时选主文件夹，或者在会话里一句话说。
- **定时任务页**（设置里，以及每个项目经理、项目的页面里各有一个筛过的列表）：每条显示名字、属于谁、频率、下次运行时间、上次结果、开关。可以新建、暂停、恢复、删除（M6 不做修改、立即运行；每次运行的结果就在项目经理的对话里，没有单独的记录）。
- **设置**：勿扰时段、通知开关、“待验收”攒多久发一次通知、安全红线清单（只能在这里改，见第 11 章）。

### 3.7 macOS 通知什么时候弹

| 事件 | 什么时候弹 |
|---|---|
| 等你处理（权限请求、审批、项目经理提问、需要选项目、故障） | 立刻弹，勿扰时段也弹 |
| 待验收 | 攒起来，默认每 30 分钟最多弹一次，写“有 N 项待验收”；勿扰时段不弹，只进收件箱 |
| 定时任务失败 | 立刻弹（它属于“等你处理”） |
| 每日汇总 | 到了弹一次 |
| 进行中的变化、agent 的普通回复 | 不弹，只更新未读数 |

- 如果用户正看着对应的对话，不弹。
- 实现方式：
  - **主要用浏览器通知**：网页开着时用浏览器的通知接口（M0 实测 `127.0.0.1` 是安全来源，可以申请通知权限），点通知跳回网页里对应的那一条。第一次打开界面时，顶部提示用户允许通知。
  - **`osascript` 只做兜底**：网页没开时守护进程用 macOS 自带的 `osascript` 发通知。M0 实测这种通知算“脚本编辑器”发的，点了只会打开脚本编辑器，不能跳到我们的页面，所以文字里写清楚“打开 agent-hub 的收件箱查看”。
  - 以后有了桌面外壳，统一改成外壳发的原生通知。

**和 Grok Bot 的异同**：Grok 在 bot 需要输入时才提醒，做完的回复不推（第三方详解 Notifications 一节）；我们一致，只对“等你处理”立即弹。不一致：Grok 推到手机；原型只有这台 Mac 的系统通知。

## 4. 整体架构

### 4.1 图

```
            浏览器（以后换成桌面外壳）
                     │  HTTP + WebSocket
                     │  127.0.0.1:界面端口，要带用户令牌
┌────────────────────┴──────────────────────────────────────────┐
│ 守护进程（一个 Node.js 进程）                                    │
│                                                                │
│  界面服务 ──命令──▶ 账本（唯一写业务表）──同一事务──▶ 动作队列     │
│     ▲                  ▲                              │        │
│     │推送变化          │命令                          ▼        │
│  通知 ◀── 收件箱变化   分拣（总助）   调度器（定时任务）  执行器    │
│                        看门狗                         │        │
│                                     ┌─────────────────┤        │
│                                     ▼                 ▼        │
│                         驱动层（Claude；以后 ACP）  worktree 管理 │
│                                     ▲                          │
│  agent 接口：给 hub 命令和权限钩子用（会话令牌）                   │
└──────────┬──────────────────────────┬─────────────────────────┘
           │ 子进程：stdin 写消息，     │ hub 命令：Unix socket
           │ stdout 读事件流            │ 权限钩子：127.0.0.1 钩子端口
           ▼                          │
     claude 进程们 ────────────────────┘
     （总助一次性调用 / 项目经理会话 / Worker 会话）
           │
           ▼
     项目文件夹、Worker 的 worktree
```

### 4.2 各部分管什么

| 部分 | 管什么 |
|---|---|
| 界面服务 | 提供网页和 WebSocket；把用户的操作变成命令交给账本；把账本的变化推给网页。只监听 `127.0.0.1`。 |
| 账本 | 唯一写业务表的模块（项目、对话、消息、工单、审批、收件箱、定时任务……）。每个命令在一个数据库事务里写完，同时把要做的动作放进动作队列。 |
| 动作队列 + 执行器 | 存“要做的事”（启动会话、给会话发消息、建 worktree、发通知、合并……），事务提交后才执行；失败按退避重试；重启后接着执行没做完的。 |
| 驱动层 | 启动、喂消息、读输出、打断、恢复 agent 进程。把各家的输出翻译成统一的事件（agent 说了话、调了工具、要权限、一轮结束、出错）。原型只实现 Claude。 |
| 分拣 | 总助的代码规则和模型分拣（第 2.1 节）。 |
| 调度器 | 定时任务（第 10 章）：守护进程里每 30 秒一次，到点的往项目经理自己的会话发一条系统消息、从现在算下次运行时间；睡眠或没开错过的只补跑一次。 |
| 看门狗 | 定期检查：长时间没动静的会话、原地打转的 Worker、超时的轮次、没人管的孤儿进程。 |
| worktree 管理 | 建、清理 Worker 的 git worktree；合并（用户批准后）。 |
| 通知 | 按第 3.7 节的规则弹 macOS 通知。 |
| agent 接口 | 给 `hub` 命令和 Claude 权限钩子用的接口。`hub` 走 Unix socket（`~/.agent-hub/run/hub.sock`）；权限钩子是 Claude 主进程发的 HTTP 请求，走一个只监听 `127.0.0.1` 的钩子端口（第 7.5 节）。每个会话有自己的令牌，守护进程凭令牌知道是谁在请求、能做什么。和界面服务分开监听，会话令牌调不了界面服务的接口。 |
| `hub` 命令 | 一个很小的独立命令行程序，agent 在自己的 shell 里调用它向系统提请求（第 8 章）。 |

### 4.3 彼此怎么通信

- **网页 ↔ 守护进程**：HTTP 加 WebSocket。网页发命令（发消息、点按钮），守护进程推送变化（新消息、卡片状态）。每条用户消息带一个网页生成的唯一编号，用来去重（第 12.1 节）。
- **守护进程 ↔ claude**：守护进程是父进程。往 `claude` 的标准输入写一行一个 JSON 的消息，从标准输出读一行一个 JSON 的事件（第 7 章）。
- **claude ↔ 守护进程（反方向）**：两条路。一是 agent 在 shell 里运行 `hub ...`，`hub` 自己从环境变量读会话令牌和 socket 路径，通过 Unix socket 连 agent 接口（第 8.1 节）；二是 Claude 自己在需要权限时调用我们配置的 HTTP 钩子（第 7.5 节）。
- **模块之间**：同一个进程里直接调用。只有账本写业务表，其他模块要改状态都通过账本的命令。

**参考**：
- 和 DeepSeek 原型一致：一个进程里分成几个模块，只有一个模块（DeepSeek 叫 Engine）写业务表；动作在同一个事务里登记、提交后才执行（DeepSeek 的 Effects 一节：“execution begins only after commit”）；单个 SQLite 文件，只由 Store 打开，目录锁防止第二个进程写（Store 一节）；启动、关闭顺序由一个组装模块负责（Runtime 一节）。
- 不一致：DeepSeek 的 Worker 执行依赖 DeepSeek Harness（DshExecutor），我们直接驱动各家官方命令行程序；DeepSeek 的入口是群聊、GitHub、邮件，我们原型只有自己的网页。

### 4.4 技术选型

- Node.js（TypeScript），一个进程。
- SQLite，一个数据库文件，开 WAL 模式。
- 网页：单页应用，由守护进程直接提供静态文件。
- 定时任务的 cron 表达式用现成的解析库，不自己写。

具体用哪个版本、哪个库，见 [m1-plan.md](m1-plan.md) 的“技术选型”。

## 5. 主流程

### 5.1 用户在项目群里说一件事，到看到验收结果

场景：用户在 agent-hub 群里说“重启守护进程以后，有时候最后一条消息会重复，查一下修掉”。项目经理是“只管理”模式。

1. **用户发消息**。网页给这条消息生成一个编号，发给守护进程。账本在一个事务里：存下消息（同一个编号来第二次就忽略）、在动作队列里放一个“把这条消息交给项目经理在这个群的会话”。网页上消息立刻出现在右边。
2. **交给项目经理**。执行器取出这个动作。项目经理在这个群的会话如果没在跑，驱动层用之前记下的会话 ID 恢复它（第 7.4 节）；如果在跑且空闲，往它的输入里写这条消息；如果正忙，先放在我们自己的队列里，等这一轮结束再写（第 7.3 节）。群里底部出现“小林 正在思考”。
3. **项目经理讨论或者直接拆活**。它读了相关代码，回复用户“我看了，问题在 X，打算这样修，验收标准是 Y，可以吗”。这条回复显示在群里。它读代码的那些操作折叠成“执行了 5 个操作”。不弹通知。
4. **用户回“可以”**。同第 1、2 步。
5. **项目经理派活**。它在自己的 shell 里运行 `hub ticket create --title "修复重启后消息重复" --goal ... --accept ...`。`hub` 带着项目经理的会话令牌请求守护进程。账本在一个事务里：建工单 #12（状态“排队中”）、在群里加一张工单卡片、放进两个动作：“建 worktree”“启动 Worker”。`hub` 立刻返回“已建工单 #12”，项目经理接着告诉用户“已派给 Worker”。
6. **建 worktree**。执行器在项目主文件夹里从主文件夹当前分支建一个新分支和 worktree（第 7.7 节）。
7. **启动 Worker**。worktree 建好后，驱动层在 worktree 里启动 `claude`，第一条消息是工单内容和汇报格式。卡片变成“进行中 · Worker 在做”，群成员里出现“Worker · 修复重启后消息重复”。
8. **Worker 干活**。它的输出全部存进工单的过程记录。看门狗盯着它：多久没有新事件、是不是在重复同一个操作。如果它要执行按自己的权限设置需要询问的命令，会触发权限请求（见第 5.3 节）。
9. **Worker 交汇报**。最后一条回复按固定格式写：状态“做完了”、摘要、提交号、测试结果、怎么验证。一轮结束后，驱动层把这条回复交给账本解析。格式不对，守护进程自动回一句“请按格式重写汇报”，最多两次；还不对就标成“汇报格式错误”，交给项目经理人工看。
10. **交给项目经理验收**。账本把工单改成“待项目经理验收”，把汇报原文作为一条消息发进项目经理的会话：“工单 #12 汇报如下……请验收。”这条和 Worker 之间的来回在群里折叠成“⇅ Worker · 修复重启后消息重复 与 小林，2 条消息往来”。
11. **项目经理验收**。它看 worktree 里的改动、自己再跑一遍测试。
    - 不合格：运行 `hub ticket reject 12 --reason ...`。守护进程用同一个 Worker 会话把理由发回去，回到第 8 步。折叠行的消息数加一。
    - 合格：运行 `hub ticket accept 12 --note ...`。工单变成“待你验收”。
12. **用户看到结果**。
    - 群里：工单卡片变成“待你验收”，项目经理发一条总结：改了什么、怎么验证的、证据。
    - 收件箱：“待验收”分组里多一条。按通知规则，攒到下一次时弹“有 1 项待验收”。
13. **用户验收**。用户在卡片或收件箱里点：
    - “通过并合并”：这一下就是合并的批准。守护进程在项目主文件夹里本地合并到当前分支，不推送（第 7.7 节），合并成功后工单变成“已完成”，worktree 删除。合并失败（有冲突、主文件夹有未提交的改动），工单回到项目经理，群里说明原因。
    - “通过”：工单“已完成”，分支保留，worktree 删除。
    - “打回”：填理由，回到项目经理。

### 5.2 用户在总助私聊里丢一件事

场景 A：用户对总助说“agent-hub 那个重复消息的 bug 修好了没”。

1. 消息存下，放进动作“分拣”。
2. 代码规则：没有 `#项目名`，不是在群里，没有 @ → 交给模型分拣。
3. 守护进程拼上下文：总助的规矩、各项目名片、进行中的工单（包括“#12 修复重启后消息重复：待你验收”）、这个对话最近 10 条、新消息。用便宜、快的模型调一次 `claude`，要求按固定 JSON 格式回答。
4. 模型回：项目 = agent-hub，处理 = 自己答，回答 = “修好了，在等你验收，点这里看”，把握 = 高。
5. 账本写分拣记录、存总助的回复。用户在总助私聊里看到回答，带一个跳到工单 #12 的链接。

场景 B：用户说“给 agent-hub 的 README 加一节怎么启动”。

1～3 同上。
4. 模型回：项目 = agent-hub，处理 = 小活直接派，工单标题 = “README 加启动说明”，目标 = ……，把握 = 高。
5. 守护进程查这个项目进行中的工单，没有碰 README 的 → 在一个事务里：建工单（来源 = 总助）、在项目群里加工单卡片和一条系统消息“总助派了工单 #13（用户在总助那里说：……）”、往项目经理会话里发一条通知“总助派了工单 #13，做完请你验收”、放进“建 worktree”“启动 Worker”。这一步不再调模型。
6. 总助回用户：“已在 agent-hub 建工单 #13，做完项目经理先验收。”
7. 之后同第 5.1 节第 6～13 步。

场景 C：用户说“我们下个月要不要把界面改成桌面应用”。

4. 模型回：项目 = agent-hub，处理 = 转给项目经理（涉及规划和取舍）。
5. 守护进程把消息转进 agent-hub 群，标注“经总助转来”，交给项目经理；总助回“转给了 agent-hub 的小林”，带跳转链接。

场景 D：用户说“帮我看看家里 NAS 的备份脚本”。

4. 模型回：对不上任何项目，候选为空。
5. 总助发卡片：“这件事归哪个项目？”按钮：最可能的两三个项目、“新建项目”。用户点“新建项目”后，弹出新建项目的表单，原消息在项目建好后自动转进新群。

用户觉得分错了：每条分拣结果旁边有“分错了”，点开选正确的项目和处理方式，守护进程撤回原来的处理（比如把还没开始的工单取消）、按新的来，并记一条纠正。

### 5.3 权限请求变成收件箱里的待办

1. Worker 想运行一个按它自己的权限设置需要询问的命令，比如 `brew install jq`。
2. Claude 在执行前调用我们配置的权限钩子，把“哪个工具、什么参数”POST 给 agent 接口的钩子端口（第 7.5 节）。
3. 守护进程先查红线：在“一律禁止”清单里 → 直接回“拒绝”，附上原因。在“已批准、还没用过”的一次性许可里 → 直接回“允许”，并把许可标成已用。
4. 都不是 → 账本建一条审批（状态“等待”）、收件箱“等你处理”加一条、群里加一张卡片，立刻弹通知。这次 HTTP 请求先挂着等。
5. 用户在限定时间内（默认 5 分钟）点了“允许一次”或“拒绝” → 直接回给 Claude，Worker 接着跑。
6. 超时没人点 → 回“拒绝”，原因写“已提交用户审批，结果会另行通知，先别重试，做别的或结束这一轮”。审批留在收件箱里。
7. 用户之后点了“允许一次” → 账本记一条一次性许可（工具名 + 参数的指纹），往这个会话发一条消息“你之前请求的 `brew install jq` 用户已批准，可以重新执行”。它重新执行时，第 3 步会直接放行。
8. 用户点了“拒绝” → 往会话发一条“用户拒绝了 `brew install jq`，原因：……”，由 agent 自己决定怎么继续。

### 5.4 守护进程重启后

1. 新进程拿到数据目录的锁，打开数据库。
2. 找出上次记录为“在跑”的 `claude` 进程，核对进程号和启动参数里的会话 ID，确认是我们的，就结束它们。
3. 动作队列里状态是“执行中”的动作改回“待执行”（每个动作都能安全地重复执行，见第 12.2 节）。
4. 被打断的会话：放进“恢复会话”动作，按工单从旧到新排。恢复时发一条说明：“守护进程重启，你上一轮被打断了。请先看一下工作区现在的状态，再接着做。”
5. 定时任务：启动时先查一次，重启期间错过的补跑一次（第 10 章）。
6. 网页重新连上后，从账本拿全量状态，界面恢复原样。

**参考**：和 DeepSeek 的 Runtime、DshExecutor 两节一致：重启后按工单从旧到新恢复被打断的工作，带一段恢复说明和没送达的输入。

```
│       └── sessions/<会话>.jsonl   # claude 输出的原始事件流
├── run/                       # 只有守护进程在跑时才有内容，权限 0700
│   └── hub.sock               # agent 接口的 Unix socket，权限 0600（第 8.1 节）
├── pm-home/<项目经理>/          # 项目经理私聊会话的工作目录（空文件夹）
└── worktrees/<项目>/<工单>/     # Worker 的 git worktree
```

- 软件的数据里，跟 agent 绑定的只有两样：**性格设定**（`personas/`）和**定时任务**（数据库里的定时任务表）。
- 对话、工单、Worker 汇报、分拣记录、审批、交接索引都在 `hub.sqlite` 里，系统自动存。
- 项目的习惯和约定在项目自己的 `AGENTS.md` 里，不在这里。软件默认不写项目仓库（例外：建 worktree 时 git 会在项目的 `.git` 里登记，Worker 的提交也写进项目的 `.git`；合并要用户批准）。
- 不存任何密钥。界面用户令牌只是本机的一个随机串：第一次启动时生成，存在 `state/ui-token`（权限 0600），之后每次启动沿用，所以守护进程重启后浏览器里的 cookie 仍然有效，不用重新打开链接。想让旧的登录全部失效，删掉这个文件再启动，就会换一个新令牌。
- socket 不放在 `state/` 里，因为 agent 要连它；它只是一个入口，不能读数据。守护进程启动时把 `run/hub.sock` 的路径用 `realpath` 解析成真实路径，再写进环境变量和设置文件（M0 实测：沙箱放行要写真实路径，macOS 上 `/var` 其实是 `/private/var`）。

### 6.2 SQLite 的表

原则：**一个文件、一张表只由一个角色写**。下表的“写者”是守护进程里的模块；“谁能让它写”说明请求从哪来。agent 和网页都不直接碰数据库。

| 表 | 存什么 | 写者 | 谁能让它写 |
|---|---|---|---|
| `projects` | 项目：名字、一句话说明、状态（进行中 / 已归档 / 已删除）、项目经理、用哪个 Claude 配置目录 | 账本 | 用户（界面）、项目经理（`hub project ...`） |
| `project_folders` | 项目挂的文件夹：路径、是不是主文件夹、加入和移除时间 | 账本 | 同上 |
| `pms` | 项目经理：名字、头像文件、模式、默认模型、性格设定文件路径 | 账本 | 用户（界面）；项目经理只能通过 `hub persona` 改模式和习惯 |
| `persona_changes` | 性格设定的每次修改：谁改的、改前改后、理由 | 账本 | 同上（改性格设定文件和写这张表在同一个命令里完成） |
| `conversations` | 对话：总助私聊 / 项目经理私聊 / 项目群，关联的项目和项目经理 | 账本 | 系统在建项目经理、建项目时自动建 |
| `messages` | 每条消息：所属对话、所属工单（可空）、发送者、内容、是否折叠、去重编号（唯一）、投递状态（排队中 / 已送达 / 处理中 / 已回复 / 已停止 / 失败，见第 7.3 节）、失败原因 | 账本 | 用户（界面）；驱动层把 agent 的输出和投递状态交给账本 |
| `agent_sessions` | 每个 agent 会话：角色、关联的对话或工单、厂商、厂商的会话 ID、工作目录、附加目录、第几代（开新会话加一）、进程号、状态（空闲 / 运行中 / 已结束 / 坏了）、是否跑完过一轮（决定下次用 `--session-id` 还是 `--resume`，第 7.4 节）、最后一次事件时间、最近一次额度信息 | 驱动层 | 驱动层自己（启动、退出、事件） |
| `tickets` | 工单：项目、标题、目标、验收标准、来源（项目经理 / 总助）、状态、Worker 会话、分支、worktree 路径、模型、预算 | 账本 | 项目经理（`hub ticket ...`）、总助分拣、用户（界面按钮） |
| `ticket_events` | 工单的每次变化：状态变化、汇报原文和解析结果、验收意见、打回理由 | 账本 | 同上，以及驱动层交上来的汇报 |
| `triage_log` | 分拣记录：哪条消息、走的规则还是模型、去了哪、理由、把握、是否被用户纠正 | 账本 | 分拣模块把结果交给账本 |
| `approvals` | 审批：类型（工具权限 / 系统动作）、谁请求的、内容、参数指纹、状态（等待 / 允许 / 拒绝 / 已用 / 过期）、处理时间 | 账本 | agent 接口（权限钩子、`hub`）建；用户（界面）处理 |
| `inbox_items` | 收件箱：档位（1～4）、指向什么（审批 / 工单 / 定时任务运行 / 提问）、状态、通知过没有 | 账本 | 随其他命令自动建和关 |
| `handoffs` | 交接：项目、从哪个会话、给哪个会话、文件路径、原因（会话太长 / 换人 / 换主文件夹） | 账本 | 项目经理（`hub handoff write`） |
| `schedules` | 定时任务：属于哪个项目经理、名字、类型（每天 / 隔一段时间）、几点或隔多久、任务说明、开关、下次运行时间、上次运行的时间和结果（已发出 / 跳过 / 失败 + 原因）、上次发出的消息编号 | 账本 | 项目经理（`hub schedule ...`）；界面下一步做 |

（11-04 不建 `schedule_runs`：每次运行的结果就是对话里带 `scheduleId` 的那条消息。）
| `actions` | 动作队列：类型、去重键、参数、状态（待执行 / 执行中 / 完成 / 失败 / 放弃）、已试次数、下次尝试时间、最后的错误 | 动作队列 | 账本在事务里登记；执行器更新状态 |
| `health` | 各模块的健康状态：连续失败次数、最后的错误 | 各模块各写自己那一行 | — |

文件的写者：

| 文件 | 写者 |
|---|---|
| `hub.sqlite` | 只有守护进程打开（内部按上表分工） |
| `config/settings.json`、`config/policy.json` | 设置模块，只响应网页上用户的操作 |
| `personas/*.md` | 账本（处理用户编辑或 `hub persona` 命令时写） |
| `handoffs/` | 账本（处理 `hub handoff write` 时写） |
| `launch/` | 驱动层（每次启动前生成） |
| `logs/sessions/` | 驱动层 |
| `worktrees/<项目>/<工单>/` | 建和删：worktree 管理；里面的文件：这张工单的 Worker |

**参考**：
- 和 DeepSeek 一致：一个 SQLite 文件；业务表只有一个写者（Engine），动作表由 Effects 写，回执由 Outbox 写（DeepSeek 的 Dependency rules、Persistence 两节）。
- 不一致：DeepSeek 有一张通用的 `kv` 表放杂项；我们不设，杂项进 `settings.json`。我们多了 `agent_sessions` 由驱动层自己写，因为进程号、最后事件时间这些更新非常频繁，交给账本来回转没有意义，而且这些字段只有驱动层知道。

## 7. 怎么驱动 Claude

### 7.1 守规矩的底线

按 Anthropic 的规定（[legal-and-compliance][cc-legal] 的 “Authentication and credential use” 一节），订阅登录只能用于 Claude Code 等官方程序的普通使用；第三方程序不能收集、保存或转发 Claude 的登录凭证或会话令牌。所以：

- 只运行用户已经装好的、未修改的官方 `claude` 程序。登录由用户自己在终端里用官方流程完成。
- 不用 Agent SDK（包括 Python、TypeScript 包和基于它的 ACP 适配器）。
- 不读、不存、不转发 `claude` 的登录信息。守护进程只做一件事：不同项目要用不同账号时，在启动 `claude` 时设环境变量 `CLAUDE_CONFIG_DIR` 指向用户自己建好的配置目录。
- **不用 `--bare`**：这个模式不读订阅登录，只认 API key（[headless][cc-headless] 的 “Start faster with bare mode” 一节）。

**参考**：T3 Code 是通过 Agent SDK 的 `query()` 驱动 Claude 的（T3 Code 文档 `docs/user/faq.md`、`docs/orchestration-v2/testing-strategy.md`），这条路我们不能走。T3 Code 用 `CLAUDE_CONFIG_DIR` 区分账号的做法（`docs/user/providers-claude.md`）我们照搬。

### 7.2 启动参数

项目经理和 Worker 用长期会话，启动命令大致是：

```
claude -p
  --input-format stream-json      # 从标准输入一行一个 JSON 收消息
  --output-format stream-json     # 往标准输出一行一个 JSON 发事件
  --verbose                       # stream-json 输出需要
  --replay-user-messages          # 一轮开始处理某条消息时回显它，用来标“处理中”
  --session-id <我们预先生成的 UUID>   # 第一次启动时用
  --resume <会话 ID>               # 之后恢复时用（二选一）
  --model <模型别名>
  --append-system-prompt-file <launch/会话/prompt.md>
  --settings <launch/会话/settings.json>
  --add-dir <附加文件夹> ...
```

- **提示词**：守护进程每次启动前生成 `prompt.md`，内容依次是：软件定的角色说明和 `hub` 命令用法（agent 改不了）、性格设定、项目信息（名字、文件夹、进行中的工单）、最近一份交接、“先读项目根目录的 `AGENTS.md`”。用“追加”而不是“替换”系统提示，保留 Claude Code 自带的能力。
  - `AGENTS.md` 那句按情况加（M0 实测：目录里没有 `CLAUDE.md` 时 Claude 会自动读 `AGENTS.md`；两个都有时只读 `CLAUDE.md`）：项目有 `AGENTS.md`、也有 `CLAUDE.md`、且 `CLAUDE.md` 里没写 `@AGENTS.md` 时才加，避免读两遍。
  - `hub` 用法里写明：直接敲 `hub ...`，不要在命令里写 `$HUB_TOKEN` 之类的变量（第 8.1 节）。
- **设置文件**：守护进程按 `policy.json` 生成 `settings.json`，用 `--settings` 传入。里面只放三样，都只跟我们自己的东西有关：
  - 权限钩子（第 7.5 节），把 agent 弹出的权限请求转给守护进程；
  - 允许规则 `Bash(hub:*)`，让 agent 跑我们的 `hub` 命令不用每次批准；
  - `sandbox.network.allowUnixSockets: ["<hub.sock 的真实路径>"]`。沙箱没开时不起作用；用户以后自己开了沙箱，`hub` 照样连得上（第 8.2 节）。

  除此以外不改 agent 自己的权限规则和沙箱设置，这些沿用各家 agent 自己的配置（第 11 章）。
- **用户全局设置会跟着进来**：`--settings` 是在用户自己的设置上**加**一层，不是替换。M0 实测，用户全局 `~/.claude/` 里的 `CLAUDE.md`、钩子（包括用户自己的 `PermissionRequest` 钩子）、插件，每个 agent 都会加载。这和“权限沿用 agent 自己的设置”一致，是有意的。影响和另一种做法见 [m1-plan.md](m1-plan.md) 的待拍板问题。
- **工作目录**：项目经理在项目里 = 主文件夹；项目经理私聊 = `pm-home/<项目经理>/`；Worker = 自己的 worktree。
- **环境变量**：`HUB_TOKEN`（这个会话的令牌）、`HUB_SOCK`（`hub.sock` 的真实路径）、需要时 `CLAUDE_CONFIG_DIR`。
- **MCP**：不加 `--strict-mcp-config`，也不传 `--mcp-config`，`claude` 按默认方式加载 MCP：用户的 claude.ai 连接器（Slack、Gmail、Google Drive、Jira 等）、用户级配置都能用。项目文件夹里的 `.mcp.json` 也可能被加载：`claude -p` 在没信任过的文件夹里也会连项目里配置的 MCP 服务器（[headless][cc-headless] 的 bare mode 一节）。已知，用户接受（11-04 用户定；此前用空配置加 `--strict-mcp-config` 挡掉它，同时也挡掉了用户的连接器）。不做白名单或只读过滤。
- ~~定时任务的运行额外加 `--permission-prompts none`~~：11-04 定时任务改成发进项目经理自己的会话，没有单独的运行，权限沿用这个会话本来的设置。

总助的分拣和汇总是一次性调用，不留会话：

```
claude -p --output-format json --json-schema <分拣结果的格式>
  --tools "" --no-session-persistence --model <便宜、快的模型>
  --strict-mcp-config --mcp-config <空配置>
```

提示词从标准输入传入。结果里的 `structured_output` 就是分拣结果；没有这个字段（比如模型拒绝了）就当“拿不准”，发卡片问用户。格式里的项目名是枚举，每次按当前进行中的项目列表生成，模型编不出不存在的项目（M0 实测 20 次输出全部符合格式）。

### 7.3 怎么传消息、读输出

**传消息**：往 `claude` 的标准输入写一行 JSON，形如：

```json
{"type":"user","message":{"role":"user","content":[{"type":"text","text":"……"}]}}
```

- **一次只写一条，等 `result` 再写下一条**。M0 实测：一轮还在跑时写进去的几条消息不会丢，但会被合并成下一轮的一条用户消息，模型常常只回应其中一条。所以每个会话在我们这边有一个待发队列：会话空闲就写；正忙就放进队列，等这一轮的 `result` 到了再写。这样我们写进去的每一行对应一轮，回复和消息对得上。
- **用户连发几条**：会话忙时用户连发的几条，等这一轮结束后由我们拼成一条写进去，开头写清“【用户连发了 3 条】”，每条前面编号。这样用户的补充下一轮就能看到，不用一条一条等。
- **系统发的消息**（Worker 汇报、审批结果、定时提醒）：同样等空闲再写，不和用户的消息拼在一起，免得打断用户正在进行的讨论。队列里用户的消息排在系统消息前面。
- **来源标注**：让 agent 分得清是谁说的。约定是：用户消息不加标签；系统消息由发它的一方（调用驱动层的地方）自己在开头带 `【…】` 标签，比如“【工单 #12 汇报】”；驱动层自己加的恢复说明、重发说明都以“【系统】”开头。驱动层不加、也不改标签。
- **写入前先校验**：M0 实测，一行不是 JSON，或者 `message.role` 不是 `"user"`，`claude` 会直接退出。驱动层统一用一个函数生成这一行（`JSON.stringify` 一个固定结构），写之前再检查一次，不合格就不写、记错误。
- **投递状态**：写进标准输入成功 → “已送达”；收到 `--replay-user-messages` 的回显 → “处理中”（M0 实测回显在这一轮开始处理它时才出来，不是收到时）；这一轮 `result` 到了 → “已回复”；被打断 → “已停止”；起不来且重试次数用完、写入前校验没过、这一轮出错或进程崩溃 → “失败”，记下原因，界面显示出来。状态只往前走，只有“失败”能在重发时回到“已送达”。
- **进程意外退出**（崩溃、被打断后退出）：这一轮按崩溃处理，下次有消息时按第 7.4 节用 `--resume` 重启。

**读输出**：一行一个事件，驱动层逐行读，原样追加到 `logs/sessions/<会话>.jsonl`，再翻译成统一事件交给账本：

| Claude 的事件 | 我们怎么处理 |
|---|---|
| `system` / `init` | 每一轮开头都会来一次（M0 实测）。第一次记下会话 ID、模型、工具列表，标记会话“运行中”；之后只更新“最后一次事件时间” |
| `user`，`--replay-user-messages` 的回显 | 对应的消息标“处理中” |
| `user`，内容是 `[Request interrupted by user]` | 标记这一轮“被打断”（第 7.4 节） |
| `assistant`，内容里有文字 | 变成一条 agent 消息显示出来 |
| `assistant`，内容里有工具调用；`user`，内容里是工具结果 | 记进这一轮的操作列表，界面折叠成“执行了 N 个操作”；顶部状态显示当前在做什么 |
| `system` / `api_retry` | 断网、过载时 claude 自己在重试。出 `api_retry` 事件（第几次 / 共几次、下次重试时间点、状态码、error），账本放进会话状态的 `apiRetry`（只在内存），网页状态行显示“网络出错，正在重试（第 3/10 次）”；下一个正常事件（agent 输出、工具调用、一轮结束）清掉。重试用完 claude 出一个 `subtype: success`、`is_error: true` 的 result，按“这一轮出错”走（消息标失败，原因是 result 里那句话；Worker 的发 turn_failed 给项目经理）。字段缺了或类型不对的整条跳过 |
| `rate_limit_event` | 每轮都有。记下各个额度窗口的 `utilization` 和 `resetsAt`，界面可以显示“5 小时额度已用 N%”；`status` 不是 `allowed` 时状态“等额度”。额度真用完时长什么样，M0 没碰上，等碰上再补 |
| `control_response` | 打断控制消息的回应（第 7.4 节），只记录 |
| `result` | 一轮结束：记下成功与否、耗时、用量、被拒绝的权限。这一轮前面有过 `[Request interrupted by user]` 的，算“已停止”，不算正常结束，不交给汇报解析。其余情况，Worker 的这一轮最后一条文字交给汇报解析。然后从待发队列里取下一条写进去 |

每个事件都有 `uuid`，消息按（会话，`uuid`）去重，重放日志也不会出现重复消息。

### 7.4 会话怎么恢复

- 第一次启动用 `--session-id` 传我们自己生成的 UUID，所以启动前就能把会话 ID 写进 `agent_sessions`。即使 `claude` 在输出第一条事件前就崩了，也知道该恢复哪个。
- **`--session-id` 只能用一次，之后一律 `--resume`**。M0 实测：同一个 ID 再用 `--session-id` 会报 `Session ID … is already in use` 并退出；`--resume` 一个不存在的 ID 会报 `No conversation found with session ID` 并退出。驱动层按 `agent_sessions` 里“是否跑完过一轮”选参数；选错了只会得到这两个明确的报错，就换另一个参数自动重试一次。
- 进程空闲 10 分钟（可设）就关掉它的标准输入，让它正常退出，释放内存。下次有消息时用 `--resume <会话 ID>` 重新启动。会话内容由 Claude 自己存在本机，`--resume` 按 ID 在本机所有项目里找（[cli-reference][cc-cli] 的 `--resume` 一条）。
- 加或删附加文件夹：下次启动时带上新的 `--add-dir`，继续用同一个会话（M0 实测：新目录生效、旧目录被拒），并在下一条消息里说明“附加文件夹改成了……”。模型自己也会被告知环境变了，这句说明不是必须，但无害，保留。
- 换主文件夹、会话太长、换项目经理：开新会话（第几代加一）。旧会话先写交接，新会话的提示词里带上这份交接。
- Claude 自己会在上下文快满时自动压缩，原型不另做处理；用户也可以在群设置里点“开新会话”，走上面的交接流程。
- **打断**：用户点“停止”时，分两步：
  1. **先写控制消息**：往标准输入写一行 `{"type":"control_request","request_id":"<我们生成的编号>","request":{"subtype":"interrupt"}}`。M0 实测：马上回一条 `control_response`，再出 `[Request interrupted by user]` 和一条 `result`，**进程不退出**，下一条消息照常跑。这是 `claude` 命令行自己的标准输入协议，不经过 Agent SDK，但官方文档没写，版本升级可能变。
  2. **5 秒内没有 `control_response` 就发 `SIGINT`**。M0 实测：`SIGINT` 会结束这一轮，**然后整个进程退出**（退出码 0），不是只停这一轮；会话保留，下次有消息时 `--resume` 接着聊，模型知道自己被打断了。
  - 不用 `SIGTERM`：M0 实测它不输出 `result` 直接退出（退出码 143）；[headless][cc-headless] 的 “Stop a run with SIGTERM” 一节也说这一轮会停在半截。
  - 打断后的那条 `result` 不当正常结束：`SIGINT` 时 `is_error: true`；控制消息时 `subtype: success` 但前面有 `[Request interrupted by user]`。驱动层按“这一轮有没有出现过这条打断消息”标“已停止”。
  - 每次升级 `claude` 后，跑一遍真 `claude` 的打断冒烟测试（第 13 章），确认控制消息还管用。

### 7.5 中途的权限请求怎么变成收件箱里的待办

Claude 在无界面模式下遇到需要批准的操作，有三种办法交给外部决定：`PermissionRequest` 钩子、`--permission-prompt-tool`（要一个 MCP 工具）、Agent SDK 的回调（[headless][cc-headless] 的 “Auto-approve tools” 一节）。我们用 **HTTP 类型的 `PermissionRequest` 钩子**：

- 不需要 MCP，不经过 Agent SDK。
- 钩子由 Claude 主进程发起，就算 agent 按自己的设置开了沙箱，也不受 shell 沙箱的网络限制。
- 写在我们生成的设置文件里，用 `--settings` 传入。

设置文件里大致是：

```json
{
  "hooks": {
    "PermissionRequest": [{
      "hooks": [{
        "type": "http",
        "url": "http://127.0.0.1:<钩子端口>/hooks/permission",
        "headers": { "Authorization": "Bearer $HUB_TOKEN" },
        "allowedEnvVars": ["HUB_TOKEN"],
        "timeout": 330
      }]
    }]
  }
}
```

- **为什么钩子走 TCP 而 `hub` 走 Unix socket**：钩子要填一个 URL，官方文档没说能填 Unix socket，M0 只验证过 TCP；而且钩子请求是 Claude 主进程发的，不受 shell 沙箱限制，所以单开一个只监听 `127.0.0.1` 的钩子端口就行；`hub` 跑在 agent 的 shell 里，开了沙箱也要能连，所以走 Unix socket（第 8.1、8.2 节）。钩子端口只接 `/hooks/permission`，要带会话令牌。
- 守护进程收到后按第 5.3 节处理，回 `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}` 或 `"deny"` 加原因（[hooks][cc-hooks] 的 PermissionRequest 一节）。M0 实测：`deny` 的原因原样回给模型。
- 请求体里有 `session_id`、`cwd`、`tool_name`、`tool_input` 等，收件箱卡片直接用这些，用 `session_id` 对回我们的会话，不用另外查。
- 守护进程挂着等用户的时间（默认 5 分钟）要比钩子的超时短，保证总是由我们回答，而不是钩子超时。M0 实测 `timeout: 330` 生效：挂 300 秒再回 `allow`，`claude` 一直等着并照做。
- **守护进程不在、连不上、超时**：不写 `onFailure`。官方文档里它的默认值是 `continue`，意思是钩子失败就按 Claude 自己的权限流程走；`-p` 下没人能回答，结果就是拒绝（M0 实测：超时时这次调用被当成拒绝）。不写它，免得以为是它在起作用。
- 用户“拒绝”的结果作为普通拒绝原因回给 Claude，由它自己决定怎么继续。
- **用户自己的 `PermissionRequest` 钩子也会跑**：`--settings` 里的钩子是加上去的，不替换用户全局设置里的钩子（M0 实测两个同时跑）。用户的钩子如果也给出决定，可能和我们的冲突。守护进程启动时检查用户全局设置里有没有 `PermissionRequest` 钩子，有就在设置页提示一句“你自己的权限钩子也会对 agent 生效”。

**参考**：Grok Bot 的审批卡片有“允许一次 / 拒绝 / 总是允许”三个选项，聊天里发起的卡片会一直等，routine 发起的 30 分钟后过期（第三方详解 Approvals 一节）。我们一致的地方：卡片、允许一次、定时任务里不挂着等。不一致：原型没有“总是允许”按钮，长期放行的规则只能在设置页的允许清单里由用户加，避免随手一点就永久放开。

### 7.6 同时跑几个

- 不设上限：要几个 `claude` 进程就启动几个，工单不用排队等名额。总助的一次性调用也一样。
- 空闲的项目经理进程 10 分钟后退出，不占内存。
- 订阅额度用完时，Claude 会把这一轮挂到额度恢复（T3 Code 文档 `docs/user/providers-claude.md` 的 Usage limits 一节）。这种等待不算卡住，看门狗跳过它，界面显示“等额度”。M0 实测 10 个 `claude` 同时跑没出问题。
- 同时跑得多，额度消耗也快；用一周后看实际消耗，再决定要不要加限制。

### 7.7 worktree 怎么建和清理

> **注（11-03 / 11-04 已改，见 [m3-plan.md](m3-plan.md) 第 1、2.3 节）**：M3 去掉了工单状态机和界面“通过并合并”按钮，系统只管在 `hub worker start` 时建 worktree；什么时候合并、怎么合并、怎么清理 worktree 系统不规定，由 agent 按项目的 `AGENTS.md` 自己判断（11-04 用户定）。下面保留最初草案备查。

**建**（工单的“建 worktree”动作）：

1. 检查项目主文件夹是 git 仓库。不是就不派 Worker：工单直接变成“需要你处理”，提示把文件夹变成 git 仓库，或者让项目经理自己做。
2. 在主文件夹里运行 `git worktree add -b hub/<工单号>-<短名> ~/.agent-hub/worktrees/<项目>/<工单号> <基准>`。基准默认是主文件夹当前分支的最新提交，项目经理建工单时可以指定。
3. 这一步可以重复执行：worktree 已经存在且分支对得上，就当成功。

**清理**：

- 工单“已完成”或“放弃”：`git worktree remove` 删除 worktree。分支保留，删分支要用户批准。
- 工单“失败”：worktree 保留 7 天，方便查原因，之后自动删除。
- 守护进程每次启动运行一次 `git worktree prune`，清掉登记了但目录已经不在的 worktree。
- 有未提交改动的 worktree 不自动删除，进收件箱问用户。

**合并**（用户点了“通过并合并”之后）：

1. 检查主文件夹没有未提交的改动。有就不合并，工单回到项目经理，说明原因。合并进主文件夹当前所在的分支。
2. 在主文件夹里运行 `git merge --no-ff hub/<工单分支>`。
3. 有冲突就 `git merge --abort`，工单回到项目经理，让它派 Worker 先基于最新的当前分支更新。
4. 不推送到远端。

**参考**：Gas Town 用 worktree 隔离并行的 agent，并有合并队列（`HANDOVER.md` 第 7 节第 2 条的调研结论）；我们原型先不做合并队列，一次合一个，合并由用户点按钮触发。

### 7.8 以后接其他厂商

驱动层对外只有几个动作：启动（新建或恢复）、发消息、打断、关闭；对内统一成几种事件：说了话、调了工具、要权限、一轮结束、出错。

- Claude：本章的做法。
- Codex、Gemini 等：走 [ACP][acp]。ACP 里对应的是新建会话、发提示、取消、加载会话，以及 agent 主动发来的权限请求，一一对得上。
- 注意：Claude 现有的 ACP 适配器基于 Agent SDK，所以 Claude 不走 ACP，一直用本章的无界面协议。

## 8. agent 怎么向系统提请求

### 8.1 原型先用命令行

agent 在自己的 shell 里运行 `hub <子命令>`。`hub` 自己从环境变量读会话令牌（`HUB_TOKEN`）和 socket 路径（`HUB_SOCK`），通过 Unix socket 请求守护进程的 agent 接口，把结果打印出来。

- **agent 只敲 `hub ...`，命令里不出现变量**。M0 实测：命令里写了 `$HUB_TOKEN` 这类变量，Claude 的权限检查会直接拒绝（“A variable in this command can't be checked before it runs”），连允许规则都不管用。所以令牌只能由 `hub` 自己去读，提示词里也写明这一点。
- 允许规则是 `Bash(hub:*)`，由我们生成的设置文件带上（第 7.2 节）。
- 通道选 Unix socket，理由和沙箱下的设置见第 8.2 节。

主要子命令（项目经理用的为主，Worker 只用到读工单）：

| 命令 | 做什么 | 要不要用户批准 |
|---|---|---|
| `hub ticket create / reply / reject / accept / cancel` | 建工单、回复 Worker、打回、验收通过、取消 | 不用 |
| `hub ticket show <号>` | 读工单和原始消息（Worker 也能用，只能读自己的工单） | 不用 |
| `hub ask-user --question ... --options ...` | 发一张“等你处理”的卡片，用户的选择作为消息回给它 | — |
| `hub project create / attach / detach / set-main / assign / archive / delete` | 项目操作（第 9 章） | 归档、删除要；建项目时文件夹不存在要 |
| `hub handoff write` | 写交接 | 不用 |
| `hub persona show / edit` | 看、改自己的性格设定 | 不用，但界面上会显示改了什么 |
| `hub schedule add / list / pause / resume / remove` | 定时任务（第 10 章），只能管自己的（M6 已做；不做 edit，要改就删了重建） | 不用 |
| `hub status` | 看自己管的项目和工单 | 不用 |

守护进程按令牌认人：令牌对应哪个会话、哪个角色、哪个项目，就只能做这个角色在这个项目里能做的事。agent 在命令里自称是谁不算数。

**为什么先用命令行，不先用 MCP**：

- 各家 agent 都能跑 shell 命令，同一个 `hub` 以后接 Codex、Gemini 不用改；MCP 每家的配置方式不一样。
- 用户自己在终端里也能跑同样的命令排查问题，方便调试和测试。
- 不需要等 MCP 服务器连上（`--mcp-config` 会让 `claude -p` 在第一轮前等服务器连接，默认最多 30 秒，见 [cli-reference][cc-cli]）。
- 风险在沙箱：agent 如果按自己的设置开了沙箱，它的 shell 默认连不到本机的服务（[sandboxing][cc-sandbox] 的网络一节）。M0 已经验证了放行的办法，见第 8.2 节。

**参考**：T3 Code 给 agent 的系统工具走的是 MCP：守护进程在 `127.0.0.1` 上开一个 HTTP MCP 服务，每个会话一个令牌，放在请求头里（T3 Code 文档 `docs/orchestration-v2/orchestrator-mcp-server.md`）。“每个会话一个令牌、按令牌认人”这一点我们照搬；通道不同，理由见上。

### 8.2 通道：Unix socket

M0 做了连通实验（[m0-report.md](m0-report.md) 实验 5），结论：**agent 连守护进程用 Unix socket**。

| 设置 | TCP（127.0.0.1） | Unix socket |
|---|---|---|
| 沙箱没开（用户现在的默认） | 通 | 通 |
| 沙箱开，网络什么都不放 | 不通 | 不通 |
| 沙箱开 + `allowedDomains` 加 `127.0.0.1` | 不通 | 不通 |
| 沙箱开 + `allowLocalBinding: true` | 通 | 不通 |
| 沙箱开 + `allowUnixSockets` 写**真实路径** | 不通 | 通 |

选 Unix socket 的理由：

- 沙箱没开时两条都通；开了沙箱两条都要专门放行。TCP 要 `allowLocalBinding: true`，那会放开本机**所有**端口，包括界面端口；Unix socket 只放行一个文件，范围小得多。
- 不占网络端口，靠文件权限（`run/` 目录 0700、socket 0600）控制，别的机器连不上。

落实到设计里：

- 守护进程在 `~/.agent-hub/run/hub.sock` 上开 agent 接口，启动时用 `realpath` 解析成真实路径，写进 `HUB_SOCK` 和设置文件。路径带符号链接时沙箱放行不生效（M0 实测：`/var/…` 不行，`/private/var/…` 才行）。
- 我们生成的设置文件里始终带 `sandbox.network.allowUnixSockets: ["<真实路径>"]`（第 7.2 节）。沙箱没开时不起作用；用户以后开了沙箱，`hub` 照样能连。
- `hub` 自己读环境变量里的令牌和路径（第 8.1 节）。
- 权限钩子不受沙箱影响，单独走 `127.0.0.1` 的钩子端口（第 7.5 节）。
- M0 原计划里的隔离项（worktree 里 `git commit` 等）按用户决定不测（第 15 章第 2 条）。

### 8.3 项目经理会话的权限设置

项目经理会话和 Worker 一样，权限沿用各家 agent 自己的设置，原型不另开沙箱；除了第 7.2 节说的 `hub` 两项，不另加规则。总助的一次性调用没有工具，不涉及。

### 8.4 Worker 汇报的固定格式

Worker 每一轮的最后一条回复，必须以这样一段结尾：

```
=== 汇报 ===
状态: 做完了 | 有问题 | 放弃了 | 有进展
摘要: 一两句话说做了什么或卡在哪
提交: <分支名> <提交号>（没有提交写“无”）
测试: <跑了什么命令，结果如何>（没跑写“未跑”和原因）
证据: <截图路径、输出摘录等，每行一条>（可以为空）
怎么验证: <用户或项目经理自己怎么确认>
问题: <状态是“有问题”时必填：需要谁回答什么>
=== 汇报结束 ===
```

- 守护进程只认最后一段，前面的文字照常显示。
- 状态是“做完了”时，提交、测试、怎么验证三项必须有内容，否则当作格式不对。
- “有进展”用于 Worker 判断应该停下来给项目经理看一眼的时候（比如做完了一半，想确认方向）。
- 格式不对：自动回一句“请按格式重写汇报”，最多两次；还不对，工单标成“汇报格式错误”，原文交给项目经理。
- 摘要控制在几百字以内，细节留在过程记录里（`HANDOVER.md` 第 2.4 节）。

选纯文本而不是 JSON：任何厂商的 agent 都能稳定写出来；人直接看也看得懂。

**参考**：DeepSeek 的 Worker 通过工具上报（Executor tools 一节）；我们用最后一条回复，理由见第 2.3 节。

## 9. 项目操作

所有操作都可以在项目经理的会话里用一句话说，由项目经理调 `hub` 执行（以后也能在项目设置页点）。每个操作都在账本里留记录，并在这个会话里发一条系统消息。一个项目经理只管一个项目，所以命令不用点项目名（11-03 改）。

| 操作 | 怎么说 / 怎么点 | 系统做什么 | 要批准吗 |
|---|---|---|---|
| 新建项目 | 在会话里说“在 `~/code/foo` 建项目”；或新建项目经理时选主文件夹 | 检查文件夹；建项目和主文件夹，挂在这个项目经理的会话上；会话的工作目录换成主文件夹，下一条消息前自动重启；会话里发“项目已建好”。已经有项目了 → 回“一个项目经理只管一个项目，请新建一个项目经理” | M2：文件夹不存在就拒绝；以后（M4）改成要用户批准创建 |
| 挂文件夹 | “把 `~/code/foo-docs` 也挂上” | 加进 `project_folders`；下一条消息前自动重启，带上新的 `--add-dir` | 不用 |
| 移除文件夹 | “foo 不用再管 docs 了” | 标记移除时间；下次启动不再带它；不删除文件夹本身 | 不用 |
| 换主文件夹 | “主文件夹改成 `~/code/foo2`” | 以后再定（M2 不做） | 不用 |
| ~~换项目、你也管一下 bar~~ | — | 11-03 拿掉了：不能把项目交给别的项目经理，一个项目经理也不能管第二个项目 | — |
| 归档 | “foo 先归档” | 建审批；批准后：停掉这个项目的所有会话，进行中的工单先问用户是取消还是等做完；项目经理移到“已归档”，只读；可以取消归档 | 要 |
| 删除 | “把 foo 删掉” | 建审批，卡片上写清楚会删什么、不删什么；批准后：项目标成“已删除”，从界面隐藏，worktree 删除，聊天记录保留 30 天后清除；**项目文件夹和分支一律不动** | 要 |

- 项目经理只能操作自己的项目。
- 用户说得不清楚，项目经理先问清楚再调命令。

**参考**：和 Grok Bot 不一致：Grok 删除 bot 会一起删掉它的 routine，且不能撤销（第三方详解 Routines 一节）；我们删除项目只删软件里的记录，不碰用户的文件，归档可以撤销。

## 10. 定时任务

> M6 第 1 步（后台 + hub 命令）起按这一章做。11-04 用户定：往简单里做——定时任务就是“到点往项目经理自己的会话发一条系统消息”，不新开会话、不建运行记录表。原来设想的每周、一次性、cron、时区、立即运行、每次运行单独记录，都不做（以后要再说）。

**能设什么**：只有两种频率。

| 类型 | 例子 |
|---|---|
| 每天 | 每天 09:00（这台 Mac 的本地时间） |
| 隔一段时间 | 每 30 分钟、每 2 小时（最短 15 分钟，最长 7 天） |

**每个定时任务有**：名字、属于哪个项目经理、频率、要做的事（一段任务说明）、开关（暂停 / 在运行）、下次运行时间、上次运行的时间和结果（已发出 / 跳过 / 失败 + 原因）。存在 `schedules` 表（迁移 0008）。

**怎么建**：

- 对话：跟项目经理说“每天早上 9 点给我一份日报”，项目经理运行 `hub schedule add --name <名> (--daily HH:MM | --every 30m|2h) --stdin`（任务说明从标准输入读）。对话里出现一条给人看的系统消息“已建定时任务：每天 09:00，日报”。删除时同样留一条“已删除定时任务：日报”。
- 项目经理的其他命令：`hub schedule list`、`hub schedule pause <编号>`、`hub schedule resume <编号>`、`hub schedule remove <编号>`。只能管自己的；Worker 不能用。
- 界面（资料页的定时任务卡片、新建表单）：下一步另做。后端已经把定时任务列表放进 `/api/state`（`schedules`），变化用 `schedule.updated`、`schedule.removed` 推给网页。

**到点怎么跑**：

1. 守护进程里一个 30 秒的定时器（启动时也先查一次），调账本的 `runDueSchedules`。到点的（`next_run_at <= 现在`、没暂停的）在一个事务里：往**这个项目经理自己的对话**写一条系统消息（标题“定时任务：名字（原定 09:00）”，正文是任务说明，meta 带 `scheduleId`）、登记 `session.send`（和 Worker 汇报进对话是同一条路，排队规矩照旧）、**从“现在”算**下一次运行时间（不是从原定时间往后推）。
2. 项目经理像收到别的系统消息一样收到它，按任务说明做，回复照常发在对话里。不新开会话，没有单独的“运行记录”：每次运行的结果就是对话里带 `scheduleId` 的那条消息和它后面的回复。
3. 上一条定时消息（排队、已送达、处理中）还没处理完这次又到点：这次记成“跳过”，不发新消息。

**失败**：这一轮出错、被打断以外的失败（`claude` 报错、起不来、发不出去）记成“失败”，对话里写一条“定时任务没跑成：名字：原因”。对话停下来、最后一条不是用户发的，网页现有的“等你”提醒（M4）就会弹通知，不另做通知。下一次到点照常再跑，不自动暂停、不自动重试。

**暂停和恢复**：暂停后到点不跑；恢复时下一次运行时间从现在算，不补跑暂停期间的。

**电脑睡着、守护进程没开错过的**：醒来（或启动）后第一次检查，只补跑一次，标题写“定时任务：名字（补跑，原定 11-03 09:00）”，然后从现在算下一次。晚了不到两个检查周期（60 秒）的不算补跑。

**每日汇报**：不默认建。用户要日报时，项目经理用 `hub schedule add` 建，任务说明用提示词里的日报模板（昨天做完了什么 / 什么在等你 / 什么在进行 / 风险）。总助的每日汇总放到 M7 再说。

**参考**：
- 和 Grok Bot 一致：routine 属于一个 bot、结果发到它的对话里、能暂停/恢复/删除。
- 不一致：Grok 的 routine 有时区、能由事件触发、保留最近若干次运行记录；原型只做每天和隔一段时间两种，不记运行记录。
- 补跑一次、不补多次：和 macOS 的 launchd（`StartCalendarInterval` 在睡眠后只补触发一次）、Linux 的 systemd（`Persistent=true`）做法一致。

## 11. 审批和安全红线

**原则**：我们不加隔离层。agent 的权限沿用各家 agent 自己的设置（Claude 用户自己的设置文件、沙箱、权限规则）；守护进程只做三件事：把 agent 自己弹出的权限请求转到收件箱，由用户批准或拒绝；自己执行的不可逆动作（合并、删除）要用户点头；不把任何凭证交给 agent。

“沿用自己的设置”包括用户全局 `~/.claude/` 里的一切：全局 `CLAUDE.md`、钩子、插件都会进每个 agent（M0 实测，第 7.2 节）。我们自己只在上面加三样：权限钩子、`Bash(hub:*)`、放行 `hub.sock`。

### 11.1 哪些动作要用户批准

默认清单写在 `policy.json` 里，只能在设置页改：

| 类别 | 动作 | 原型里怎么拦 |
|---|---|---|
| 不可逆 | 合并到当前分支 | 只有守护进程合并，触发条件是用户点“通过并合并” |
| 不可逆 | 删除分支、删除项目、归档项目 | `hub` 命令建审批，守护进程批准后才执行 |
| 不可逆 | 删除工作区以外的文件 | 看 agent 自己的权限设置；它弹出请求就走权限钩子 → 收件箱 |
| 对外 | `git push`、发任何消息、发帖、发邮件 | 守护进程自己不推送、没有对外渠道；agent 自己弹出的请求走权限钩子 → 收件箱 |
| 改环境 | 安装软件（`brew`、`npm -g`、`pip` 全局安装等）、改系统设置 | agent 弹出请求就走权限钩子 → 收件箱 |
| 花钱 | 任何会产生费用的操作 | 原型里只有 Claude 本身的用量，由订阅额度兜底；其他走权限钩子 |
| 新地方 | 建项目时创建不存在的文件夹 | `hub` 命令建审批 |

agent 按自己的设置不弹请求、直接做的事（比如在自己的工作区里读写文件、`git` 的本地操作、`hub` 命令），守护进程不过问。

### 11.2 一律禁止（不给批准按钮）

守护进程在权限钩子里见到下面这些请求，直接回“拒绝”，不进收件箱：

- 读 Claude 的登录信息：`claude` 配置目录里的凭证文件、`security` 命令（读钥匙串）。
- 读写 `~/.agent-hub/state/`。
- 读 `~/.ssh`、`~/.aws`、`~/.config/gh` 等常见凭证目录。

这份清单只管得到钩子的请求。agent 按自己设置不弹请求的操作，我们拦不住（见 11.3 的局限）。

### 11.3 凭证放在哪里

“审批的关口放在凭证上”：守护进程不把凭证交给 agent。原型里具体是：

| 凭证 | 放在哪 | 谁能用 |
|---|---|---|
| Claude 登录 | `claude` 自己管（钥匙串或它的配置目录） | 只有 `claude` 进程自己；守护进程不读，也不交给 agent |
| 界面用户令牌 | `state/ui-token`（权限 0600），第一次启动生成，之后沿用；删掉文件就换新的 | 浏览器（通过守护进程打开界面时给的链接）；守护进程不交给 agent |
| 会话令牌 | 只在内存里，通过环境变量交给对应的 `claude` 进程 | 只能代表这一个会话 |
| git 远端凭证（ssh、`gh`） | 原型不用，守护进程不交给 agent | 无 |
| 以后的 GitHub、飞书等令牌 | macOS 钥匙串里守护进程自己的条目 | 只有守护进程，执行用户批准过的动作时用 |

**原型的局限**（要告诉用户）：agent 和用户用同一个 macOS 系统账号，所以守护进程“不交给”不等于“agent 拿不到”：agent 自己去读用户的文件（`~/.ssh`、钥匙串、`state/` 等）、读同账号其他进程的环境变量，我们拦不住，只能靠 agent 自己的权限设置和用户的信任。要真正隔开，得给 agent 单独开一个 macOS 用户，原型不做。

### 11.4 审批接口和红线放在哪里

- 红线在 `state/config/policy.json`，只在设置页由用户改；守护进程每次启动 `claude` 时据此生成设置文件（权限钩子，加上第 7.2 节说的 `hub` 两项），用 `--settings` 传入。
- 性格设定写什么都改不了红线：性格设定只是追加的提示词，红线由守护进程在钩子里执行。
- 审批接口只在界面端口上，要带界面用户令牌；会话令牌调不了审批接口，所以 agent 通过 `hub` 批准不了自己的请求。（同账号的 agent 自己去读 `state/ui-token`，见 11.3 的局限。）

**参考**：
- Grok Bot 用“自动审核 + 规则（自动允许 / 先问）”决定要不要问人，“先问”优先（第三方详解 Approvals 一节）。我们一致：规则分“要问 / 禁止”，冲突时更严的优先。不一致：Grok 有一个模型做自动审核，我们原型没有，完全按规则来，更可预期。
- DeepSeek 原型的架构文档没写凭证放在哪里，只提到 worker 的 shell 通过命令垫片和 git 凭证助手运行（Modules 一节的 Environment）。

## 12. 可靠性

| 机制 | 原型做到什么程度 | 不做的 |
|---|---|---|
| 消息去重 | 用户消息带网页生成的编号，数据库唯一约束；agent 输出按（会话，`uuid`）唯一；Worker 汇报按（工单，那一轮的 `uuid`）唯一；通知按收件箱条目只发一次 | 跨设备去重（原型只有一个网页） |
| 动作队列 | 所有副作用都先登记再执行；事务提交后才执行；同一类型同一去重键只有一行；按类型退避重试；重启后接着执行 | 优先级之外的复杂调度 |
| 重启接着做 | 第 5.4 节的步骤全部做 | 守护进程崩溃时正在写一半的 `claude` 输出：以 `claude` 自己存的会话为准，我们只补发恢复说明 |
| 看门狗 | 下面列的几项检查 | 自动判断 agent 的结果质量 |
| 健康状态 | 每个模块连续失败 3 次就在设置页标红，并进收件箱 | 外部监控 |

### 12.1 消息去重

- 网页发消息时自带编号，断网重发也是同一个编号，数据库里只会有一条。
- 驱动层把事件交给账本时带上 `uuid`；重放日志或重复读取不会重复入库。
- 往 `claude` 写的消息，写进标准输入算“已送达”，收到回显算“处理中”，这一轮的 `result` 到了算“已回复”（第 7.3 节）。如果写进去以后、`result` 到来以前守护进程挂了或 `claude` 崩了，就不知道这条处理完没有。恢复时把这条再发一次，前面加一句“如果你已经处理过这条，忽略它”。这里选择“至少一次”，代价是偶尔多说一遍。

### 12.2 动作队列

和 DeepSeek 的 Effects 一节基本一致：命令在事务里登记动作，提交后执行；同一类型同一个键只有一行，重复登记只更新参数。

| 动作 | 去重键 | 失败怎么办 |
|---|---|---|
| 启动或恢复会话 | 会话 ID + 第几代 | 5 秒起翻倍，到 5 分钟，3 次；还不行，工单“失败”，进收件箱 |
| 给会话发消息 | 消息编号 | 会话起不来时跟着上一条重试 |
| 分拣 | 消息编号 | 2 秒起翻倍，到 60 秒，3 次；还不行，发卡片让用户自己选项目 |
| 建 worktree | 工单号 | 3 次；还不行，进收件箱 |
| 合并 | 工单号 | 不重试；失败直接回到项目经理 |
| 发通知 | 收件箱条目 | 2 秒起，3 次；失败只记录 |
| 运行定时任务 | 定时任务 + 计划时间 | 见第 10 章 |

- 工作区还没建好、额度用完这类“现在不行、等等就好”的情况，推迟执行，不算失败（DeepSeek 叫 `Later`）。
- 每个动作执行前都检查“是不是已经做过了”，做过就直接标完成。比如启动会话前看进程是不是已经在跑。

### 12.3 重启后怎么接着做

见第 5.4 节。另外：

- 关机时（收到 `SIGTERM`）：先停止接新动作，给所有 `claude` 发 `SIGINT`（M0 实测：结束当前这一轮后进程退出，会话保留，正好是关机要的），空闲的进程关掉标准输入；等最多 10 秒，还没退出的强制结束，再关数据库。下次有消息时 `--resume`。
- `claude` 是守护进程的子进程，放在单独的进程组里，守护进程意外退出后，下次启动能按进程组找到并结束它们。

### 12.4 看门狗

每 30 秒检查一次：

| 检查 | 默认阈值 | 发现后 |
|---|---|---|
| 会话一轮里多久没有新事件 | 15 分钟 | 按第 7.4 节打断这一轮（先控制消息，不行再 `SIGINT`），然后发一条“你上一轮很久没有动静，被系统停了，请说明情况”；再犯，工单“卡住了”进收件箱 |
| 同一个工具调用（工具 + 参数一样）连续出现 | 5 次 | 同上，说明是“原地打转” |
| Worker 一张工单的总时长 | 2 小时 | 停掉，进收件箱问用户是继续还是放弃 |
| Worker 的轮次 | 每轮 `--max-turns` 200 | Claude 自己会停，汇报算“有问题” |
| `claude` 启动后多久没有 `init` 事件 | 60 秒 | 结束进程，按启动失败重试 |
| `claude` 退出了但这一轮没有 `result` | — | 按崩溃处理：退避后恢复会话，带恢复说明 |
| 记录为运行中、实际已不在的进程 | — | 改成“已结束”，按崩溃处理 |
| 等额度 | — | 不算卡住，不处理 |

**参考**：DeepSeek 的架构文档里没有单独叫“看门狗”的模块，相近的是 Eval 超时后重排两次、第三次记为不可用（Engine 一节），以及每个部分一行健康状态（Dependency rules 一节的 HealthBoard）。我们的健康状态照搬；看门狗的检查项参考 Gas Town 对卡住的 agent 的处理思路（`HANDOVER.md` 第 7 节第 2 条）。

## 13. 测试方案

**两种测试**：

- **自动测试**：用一个假的 `claude` 程序（脚本），按预先写好的剧本从标准输入读消息、往标准输出写 stream-json 事件，可以按剧本崩溃、超时、发权限请求、报错。守护进程启动它和启动真 `claude` 走完全一样的代码。这样每个场景都能稳定重现。剧本从真 `claude` 的输出录下来再改（和 T3 Code 录制、回放 Claude 输出做测试的思路一致，见其 `docs/orchestration-v2/testing-strategy.md`）。假 `claude` 要照 M0 实测的行为来：每一轮开头发 `system/init`；忙时收到的几条消息合并成下一轮；坏的输入行直接退出；收到 `interrupt` 控制消息回 `control_response`；收到 `SIGINT` 结束这一轮后退出。M0 的记录和脚本（`experiments/m0/`）就是第一批剧本的来源。
- **真机冒烟测试**：用真 `claude` 跑少数几条主流程，每个里程碑验收时手动跑一遍，确认剧本没跟真实行为脱节。

| B9 | 分拣拿不准 | 自动：模型回“把握低” | 发卡片问，不自动处理 |
| B10 | 分错纠正 | 自动：点“分错了”改到另一个项目 | 未开始的工单取消；按新的处理；纠正有记录 |
| B11 | 删除项目 | 自动：批准删除 | 项目文件夹、分支都还在；worktree 没了；界面看不到 |
| B12 | 文件夹被移走 | 自动：删掉项目的附加文件夹后启动会话 | 不带这个 `--add-dir`；群里提示文件夹不在了 |

### 13.3 出错情况

| 编号 | 测什么 | 怎么触发 | 期望 |
|---|---|---|---|
| E1 | agent 进程崩溃 | 自动：剧本中途退出，没有 `result` | 退避后恢复会话，带恢复说明；连续 3 次失败，工单“失败”，进收件箱并弹通知 |
| E2 | 守护进程重启 | 自动：Worker 跑到一半时杀掉守护进程，再启动 | 旧 `claude` 进程被结束；会话被恢复，带恢复说明；界面上消息不重复、不丢 |
| E3 | 重启时动作执行到一半 | 自动：在“建 worktree”执行中杀掉守护进程 | 重启后重做一次，结果和只做一次一样 |
| E4 | `claude` 报错 | 自动：剧本发 `api_retry`（`overloaded`）后 `result` 带 `is_error` | 按退避重试；界面显示“重试中” |
| E5 | 需要重新登录 | 自动：剧本发 `authentication_failed` | 不重试；收件箱“等你处理”：请在终端里自己登录 `claude`；守护进程不碰任何凭证 |
| E6 | 额度用完 | 自动：剧本发 `rate_limit` 后长时间不动 | 状态“等额度”；看门狗不停它；额度恢复后接着跑 |
| E7 | `claude` 超时没动静 | 自动：剧本 15 分钟不输出 | 看门狗按第 7.4 节打断，再发说明；再犯进收件箱 |
| E7a | 用户点“停止” | 自动：剧本收到 `interrupt` 控制消息就回 `control_response`、打断提示和 `result` | 进程还在；消息标“已停止”；下一条消息照常跑 |
| E7b | 控制消息没回应 | 自动：剧本不理控制消息 | 5 秒后发 `SIGINT`；进程退出；下一条消息用 `--resume` 重启 |
| E7c | 打断在真 `claude` 上还管用 | 真机：每次升级 `claude` 后，让它写长文，3 秒后点“停止” | 和 E7a 一样；不一样就说明内部协议变了 |
| E8 | 启动卡住 | 自动：剧本不发 `init` | 60 秒后结束，按启动失败重试 |
| E9 | 原地打转 | 自动：剧本连续 5 次同样的工具调用 | 看门狗停下这一轮并说明 |
| E10 | 权限请求被拒 | 自动：权限钩子请求后用户点“拒绝” | Claude 收到拒绝和原因；会话继续；审批记成“拒绝” |
| E11 | 权限请求超时 | 自动：5 分钟没人点 | 回“拒绝 + 已提交审批”；之后点“允许一次”，会话收到消息，重新执行时直接放行，许可变成“已用” |
| E12 | 一次性许可不能复用 | 自动：批准后同样的命令执行两次 | 第二次又要批准 |
| E13 | 守护进程不在时的权限请求 | 真机：钩子端口没人监听时让 agent 跑一个要批准的命令 | 被当成拒绝（第 7.5 节），会话继续 |
| E14 | 电脑睡着错过定时任务 | 自动：把调度器的时钟往后拨 3 小时，中间错过 3 次 | 只补跑 1 次，标“补跑”，注明错过的时间点 |
| E15 | 真机睡眠 | 真机：设一个 5 分钟后的任务，合上盖子 10 分钟再打开 | 打开后 1 分钟内补跑 |
| E16 | 定时任务失败 | 自动：剧本报错 | 重试一次；仍失败进收件箱并立即弹通知；连续 3 次自动暂停 |
| E17 | agent 想批准自己的请求 | 自动：用 Worker 的会话令牌调审批接口 | 被拒 |
| E18 | 冒用别人的令牌 | 自动：用 Worker 的令牌调 `hub ticket accept` | 被拒（Worker 不能验收） |
| E19 | 开两个守护进程 | 自动：已有一个在跑时再启动一个 | 第二个拿不到锁，报错退出 |
| E20 | 网页断线 | 自动：断开 WebSocket 一分钟后重连 | 界面补齐断线期间的变化，不重复 |
| E21 | 会话参数选错 | 自动：剧本对 `--session-id` 报“already in use”，或对 `--resume` 报“No conversation found” | 自动换另一个参数重试一次，成功后会话照常 |

## 15. 已拍板的决定

1. **第二个试点项目**：用户的一个个人 TypeScript 项目：git 仓库、有测试、最近常改。这样不涉及公司代码，Worker 交的“测试结果”也有意义。

2. **agent 的隔离**：不另做隔离，agent 的权限沿用各家 agent 自己的设置。守护进程不把凭证交给 agent，但 agent 和用户用同一个系统账号，它自己去读是拦不住的（第 11.3 节）。agent 自己弹出的权限请求照样转到收件箱。M0 不再验证隔离，只验证 `hub` 能不能连上守护进程；结论是走 Unix socket（第 8.2 节）。

3. **验收通过后谁合并**：（**11-04 已改**：系统不规定合并流程，推送、合并前问不问用户也由 agent 按项目的 `AGENTS.md` 自己判断，见 [m3-plan.md](m3-plan.md) 第 2.3 节。原草案：用户点“通过并合并”，守护进程在项目主文件夹里本地合并到当前分支，不推送；主文件夹有未提交的改动或有冲突时不合并，交回项目经理，第 7.7 节。）

4. **同时跑几个 `claude`**：不设上限。额度用完的处理保留：状态显示“等额度”，看门狗不停它（第 7.6 节）。

5. **守护进程要不要常开**：M1～M5 手动启动，不改系统设置，错过的定时任务靠补跑兜底；M6 再装开机自启（macOS 登录项）；插电不睡眠以后由用户决定。
