# Bellwood

Cross-platform multi-agent workbench for macOS, Windows, and Linux. **Router** aggregates pending decisions and deliveries across projects and computers, while each project has one **Project Manager (PM)** that dispatches short-lived **Worker** agents (`Pieces`) across multiple model CLIs and an outbound Feishu channel. Internal package names and the default data directory keep `agent-hub` and `hub` for upgrade compatibility; see `docs/README.md` for the naming map and documentation index.

## Directory layout

- `src/daemon/`: Local daemon, SQLite ledger, Task Graph scheduler, HTTP and WebSocket servers, Feishu persistent WebSocket channel, OS sandboxes, and vendor config sync.
- `src/vendors/`: Vendor CLI drivers, protocol adapters, model catalogs, and config sync modules.
- `src/web/`: React workbench and UI component primitives in `src/web/ui/`.
- `src/hub/` and `src/feishu/`: `hub` CLI called by agents and the terminal Feishu setup tool.
- `src/mesh/` and `src/relay/`: Account login and device CLI in `src/mesh/`, device trust, mutual TLS, and Feishu hub leases in `src/daemon/mesh/`, and Node and Cloudflare relays in `src/relay/`.
- `src/shared/`: Shared types, numeric limits in `limits.ts`, pixel art assets, and pure functions.
- `apps/`: Desktop supervisor contract in `desktop/`, native macOS Swift shell in `macos/`, and Windows Rust and Tauri shell plus sandbox helpers in `windows/`.
- `migrations/`: Ordered SQLite schema migrations and `manifest.sha256` checked at startup (`docs/ledger-database.md`).
- `test/tester/`: Resident-bench AI tester runner, flow catalog, vendor readiness probe, Feishu driver, and `remote-command.sh` (`.agents/skills/tester/SKILL.md`, `docs/ai-tester-design.md`).

## Engineering standards

- **Fix root causes.** Fix each defect at the boundary where wrong state originates. Delete superseded code, docs, and prompt text in the same PR so old and new paths never coexist.
- **Centralize shared rules.** Keep backend and cross-layer thresholds and caps in `src/shared/limits.ts`, web-only UI constants in `src/web/limits.ts`, agent prompts in `src/daemon/prompt.ts`, and vendor launch arguments in `src/vendors/<vendor>/`. Never import `src/shared/limits.ts` from `vitest.config.ts` or `vite.config.ts`.
- **Prefer established libraries.** Use `zustand` for client state, `@tanstack/react-query` for fetching and query caches, Radix and `shadcn/ui` patterns for UI primitives, and `lru-cache` for bounded caches instead of custom state machines, eviction loops, or pagination glue. Check `docs/dependencies.md` before adding a package and update it in the same PR whenever dependencies change (`src/direct-dependencies.test.ts`). See `docs/dependencies.md#ui-primitives-srcwebui` for UI primitives.
- **Keep shipped text project-agnostic.** Agent prompts, the Task Graph skill, the review checklist, `hub` help and errors, system notes, and vendor-injected text ship to every user's project. They must hold for any language, build tool, trunk and remote name, code host or none, missing git or CI, and Windows PowerShell or cmd as well as POSIX shells. Rules only this repo or team needs go in `AGENTS.md`, `REVIEW.md`, or `.agents/skills/`. `src/prompt-portability.test.ts` fails names such as `origin/main`, `pnpm`, `gh pr`, or heredocs written as universal instructions and allows them as examples or under a condition that names the trait; `REVIEW.md` covers judgment calls.
- **Follow the UI standard.** Match `docs/ui-standard.md` for spacing, border radius, type scale, palette, control height, focus states, and alignment. Update `docs/ui-standard.md` first when a screen needs a pattern it does not yet cover.
- **Language policy.** Use English for source code comments, Web UI copy, `AGENTS.md`, `REVIEW.md`, `docs/`, commit messages, and PR descriptions. Keep `README.zh-CN.md`, Feishu user cards, and agent-user chat or internal agent prompts in Chinese.
- **Minimal comments.** Do not write comments that restate code, echo type signatures, add section banners (`// ----`), or cite doc section numbers. Write a concise one-line English comment only for a non-obvious *why* (such as a security invariant, concurrency subtlety, or OS or vendor quirk) that types and names cannot express.
- **Small modules and functions.** Do not build multi-thousand-line factory closures or giant functions; keep modules focused and functions short with explicit typed parameters instead of large shared mutable closures. `src/code-hygiene.test.ts` enforces the comment rules and size caps: new files at or under 1,000 lines (including `.swift` and `.rs` under `apps/`), `.ts` functions at or under 250 lines, and `.tsx` components and functions at or under 300 lines. Legacy oversized entries in `src/code-hygiene.baseline.json` cannot grow.

## Caches and state bounds

Every cache, state snapshot, and growing collection must satisfy all four rules (guarded by `src/web/selectors-cache.test.ts`, `src/daemon/store/db-cache.test.ts`, and `src/web/sw-rules-cache.test.ts`):

1. **Invalidation.** Invalidate entries promptly when underlying files, configs, or ledger rows change, and clean up session state on exit or deletion. Keep failed or empty lookups only for a short retry backoff such as `FETCHED_QUOTA_RETRY_MS`, never as normal cached values.
2. **Upper bounds.** Size in-memory collections, single API responses, and command output for one month of continuous use: 300 finished Workers, 30,000 messages, and 50,000 step logs. Put cap constants in `src/shared/limits.ts` (web-only in `src/web/limits.ts`), and compress large responses.
3. **Stable front-end references.** Selectors and hooks must return the same object reference when inputs have not changed (for example through a `WeakMap` keyed on the input object) so child `memo` boundaries hold.
4. **Measured verification.** For performance or wide-impact changes, measure before and after numbers using `.agents/skills/benchmark-checklist/SKILL.md` and `blast-radius`, and record them in the PR.

## Testing, review, and merge

Full rules for local test selection, layered CI workflows, parallel independent review, prompt-cache gates, `REVIEW.md` updates, and post-merge delivery live in [`docs/review-and-merge.md`](docs/review-and-merge.md). Core rules for every session:

- **Local verification.** While iterating, run only the targeted test files or screenshot target (`pnpm exec vitest run <file>`, `pnpm ui:polish shots --only <target>`). Do not loop `pnpm test:related`, full `pnpm ui:polish`, or benchmarks after small edits. Run the full local gate (`pnpm lint`, `pnpm typecheck`, `pnpm test:related`, and `pnpm verify` per `.agents/skills/verify/SKILL.md`) once right before the final push; never replace that final `pnpm test:related` pass with hand-picked test files. Run `src/shared/write-scope.test.ts` on sandbox or write-scope changes, and `pnpm tester` on the resident test bench (`.agents/skills/tester/SKILL.md`) on Feishu, mesh, relay, or vendor driver changes. Add new tree-scanning guards to `ALWAYS_RUN_TESTS` in `scripts/test-related.ts`. Rerun `pnpm install` inside a Worker sandbox only when `package.json` or `pnpm-lock.yaml` changed. Never use `gh run rerun` to hide flaky tests.
- **Cloud checks and handoff.** Implementation Workers push to the branch and hand off right away so parallel review and cloud CI run together. Exception: wait for the PR's CI checks with `node scripts/wait-checks.ts [PR]` (never `gh pr checks --watch`) before reporting done when the PR touches platform code that this machine cannot test (Linux `bwrap`, Windows native, or desktop packaging), when the final `pnpm test:related` lists test files that the sandbox made skip, or when the PR has no immediately following review step. A red check is yours to fix (including platform jobs this machine cannot run); if the same failure is red on `main` or flaky, report it as a problem instead of reporting done.
- **Independent review.** Each round runs logic review (`src/shared/review.ts` and `git show origin/main:REVIEW.md`, different vendor from implementation) and real-environment review (every acceptance scenario from the design plan with video or start-to-finish screenshot sequence — or a listed `not verified` record when unavailable — real vendor CLIs, prompt-cache `TokenUsage.cacheRead` hard gate, at most one local run at a time) in parallel, waiting for both tracks before aggregating. PRs changing only documentation and repository rules run logic review only. Only `[Important]` fails. Every `[Important]` fix adds a reproducing regression test or structural guard in the same PR. After 3 rounds with an open `[Important]` finding, stop and have the Project Manager escalate to the user with a decision card. See [`docs/review-and-merge.md#independent-review`](docs/review-and-merge.md#independent-review).
- **Merging and post-merge.** Never push directly to `main`, and never merge a draft. Squash-merge only after all checks (including path-filtered Windows and desktop jobs that ran) and required reviews pass, no hard gate is unresolved, and PRs touching paths under "Paths that require a review stamp" in `REVIEW.md` carry a `bellwood/review` `success` stamp (`node scripts/post-review-stamp.ts`, then squash-merge without waiting for user approval to merge). After merge, the Project Manager delivers the acceptance evidence package to the conversation and Router, runs `hub graph finish` only after the PR merges, and runs `hub self-reload` (with `--build` when `src/web/` changed) for daemon or web UI changes. See [`docs/review-and-merge.md#merging-and-post-merge`](docs/review-and-merge.md#merging-and-post-merge).

## Plans, commits, and pull requests

- **Plan first.** Tasks that call for a design plan deliver `docs/<topic>-design.md`, a compiling code skeleton, and runnable acceptance tests on the same branch with a recorded pre-implementation baseline per `docs/plan-standard.md` (for complex tasks, the Project Manager may assign two independent design Workers on different vendors followed by a synthesis Worker). The Project Manager reviews and approves plans, escalating to the user only for user-visible behavior or interface changes, multi-fold foundation rebuilds, or irreversible or external-facing operations. Implementation steps fill in bodies until every acceptance test passes without modifying or weakening planning tests.
- **Commit and PR discipline.** Project Managers coordinate with `.agents/skills/poteto-mode/SKILL.md`; Workers do not load `poteto-mode` and follow their task brief and these rules directly. Split commits, structure PR descriptions, and fill `.github/pull_request_template.md` per `.agents/skills/poteto-mode/playbooks/opening-a-pr.md` and `.agents/skills/technical-writing/SKILL.md`, stating the user goal in the first sentence of `## Why`. Design documents (`docs/*-design.md`) may name reference products; PR descriptions, commit messages, UI copy, and code comments must not. Read your full diff before committing, removing AI filler per `.agents/skills/unslop/SKILL.md` and redundant comments per `.agents/skills/no-comments/references/comment-sicko.md` without spawning subagents.
- **PR lifecycle and description sync.** The Project Manager opens a draft PR (`gh pr create --draft`) after a plan is pushed, all subsequent implementation and fix steps push to that same branch, and the PR is marked ready (`gh pr ready`) once ready for review and the user has approved any decision that requires their approval. Open non-plan PRs ready for review (overriding the readiness rule in the `pstack` PR playbook). Update a PR description by pushing an annotated `pr-body/<PR>` tag (`docs/review-and-merge.md#updating-a-pr-description`).

## Repository skills

`<repo>/.agents/skills/` is the single canonical skill directory (`.claude/skills` is a symlink to `../.agents/skills`). Preserve Bellwood-specific `verify/` and `tester/` alongside `PSTACK-LICENSE` when updating upstream `pstack` (`docs/dependencies.md#repository-skills-pstack`).
